# 講師デモ：Azure Backupによる別VMへの復元

ASRの初期複製・再保護などの待ち時間に実施する補足デモです。参加者が操作するハンズオンではありません。**ASRとは別の講師用Ubuntu VMでAzure Backupを事前に有効化し、HTML変更前・変更後の復旧ポイントを取得**しておきます。当日は変更前のポイントを選んで新しいVMを作成し、現在の元VMとは異なる過去の状態へ戻せることを確認します。環境構築・バックアップ取得・HTML変更は事前準備に含めます。

> 手順書は準備用の叩き台です。Azure上での動作確認済みを意味しません。講師が事前に同じ構成で復元を完走し、Portalの表示、復元先設定、接続経路、実測時間を確定してから使用します。

初期環境は[デモ用Bicepのデプロイ手順](./infra/README.md)で作成できます。VM・ネットワーク・Azure Backup保護設定まで自動構成します。Apache・正常HTMLの構成、変更前・変更後のバックアップ取得と別VMへの復元は、以降の手順で手動実施します。

## 1. 目的と説明のポイント

| 観点 | ASRハンズオン | このBackupデモ |
|---|---|---|
| 想定シナリオ | 元の稼働先が使えない | 稼働中のVMから、HTML変更前の状態を取り出したい |
| 主な操作 | 別リージョンへのフェールオーバー・再保護 | 復旧ポイントを選択し、新しいVMへ復元 |
| 確認すること | 稼働先を切り替えて運用を続けられるか | バックアップ時点のOS・アプリ・データを戻せるか |

- 複製先にも誤更新が反映され得るため、レプリケーションとバックアップは補完関係です。ASRにも過去の復旧ポイントはありますが、長期保持用のバックアップを代替するものではありません。
- バックアップ有効化だけでなく、**復元後のWeb応答とデータまで確認**します。
- 「任意の復旧ポイント」は、**取得済みで保持されている、復元条件を満たすポイントの中から選ぶ**という意味です。任意の時刻を指定してVMを巻き戻せるわけではありません。
- 新しいVMへ復元するため、元VMの現在の内容を上書きせずに過去の状態を確認できます。今回は最新ではなく、HTML変更前のポイントを選ぶことを見せ場にします。
- 今回は同じリージョンへの復元です。リージョン障害からの復旧、Cross Region Restore、DNS切り替え、業務全体の復旧は検証しません。
- ファイル単位の復旧は本編に含めません。別VMへの復元に絞り、Linuxのファイル復旧スクリプト転送・iSCSI接続などの準備を増やさない構成にします。

## 2. デモの進め方と時間枠

当日の説明・操作は**15〜20分程度を目標**にします。バックアップ・VM復元の待ち時間は別で、完了時間は保証しません。

| 目安 | 当日の内容 |
|---|---|
| 3分 | Backup有効化済みの元VMと、現在の変更後HTMLを確認 |
| 3分 | 変更前・変更後の復旧ポイントを示し、戻す時点を選ぶ |
| 5分 | 変更前のポイントから別VMへの復元を開始 |
| 5分 | 復元VMのApache・HTMLと元VMを比較 |
| 2分 | RTO／RPOの確認範囲、後片付けの注意 |

### 待ち時間が長い場合

事前リハーサルで復元したVMを、結果確認用として用意しておきます。当日用とは名前を分けます。

1. 当日は新しいVMへの復元を開始し、ジョブの進捗を見せます。
2. 時間枠内に完了しなければ、**「当日のジョブは実行中。ここからは事前に同じ復旧ポイントから復元したVMで結果を確認する」**と説明して切り替えます。
3. 当日ジョブの成功とは扱いません。失敗した場合はエラーを表示・記録し、事前VMの表示で成功扱いにしません。
4. ASRの参加者操作を再開できる状態になったらデモを区切ります。当日ジョブの結果は後で確認し、未完了・失敗も記録します。

## 3. 構成と開始前の確認

```text
講師専用・同一リージョン

元VM：Ubuntu + Apache + index.html
  │
  └─ Azure Backup ──> Recovery Servicesコンテナー
                         │ HTML変更前・変更後の復旧ポイント
                         │ 今回は変更前を選択
                         ├─ 事前復元VM：結果確認用
                         └─ 当日復元VM：当日の新規ジョブ

復元VMは専用の復元先VNetへ配置
ASRの元VM・DR用VNet・コンテナーは使用しない
```

### 講師が事前に決める値

名前の末尾に講師が決めた英数字の識別子を付けます。以下は命名例で、既存のリソース名を流用しません。

| 項目 | 例・選び方 |
|---|---|
| 元VM・コンテナー用RG | `rg-backup-demo-source-<id>` |
| 復元先RG | `rg-backup-demo-restore-<id>` |
| 元VM | `vm-backup-demo-source-<id>` |
| 事前復元VM | `vm-backup-demo-rehearsal-<id>` |
| 当日復元VM | `vm-backup-demo-live-<id>` |
| Recovery Servicesコンテナー | `rsv-backup-demo-<id>` |
| 元VNet／復元先VNet | それぞれ専用に作成。相互・業務ネットワークとのピアリングなし |
| OS・ディスク | Ubuntu Server 22.04 LTS Gen2、OS管理ディスクのみ。カスタムイメージなし |
| セキュリティの種類 | Trusted Launchを想定。バックアップ・新規VM復元の対応条件を事前確認 |
| ポリシー | 対応するEnhancedポリシーで日次バックアップ。保持期間・スナップショット保持期間を記録 |
| コンテナーの冗長性 | 同一リージョンのデモとしてLRSを想定。保護開始前に確定 |
| ステージング用ストレージ | 復元画面で必要な場合に使用。コンテナーと同一リージョンの専用Standard汎用v2アカウント |
| OS接続 | 各VNetのBastionなど、承認済み経路 |
| Web確認 | 講師の端末から専用公開IPへのHTTP、または承認済みプライベート経路 |

### 開始条件

- [ ] 講師用サブスクリプション、リージョン、費用、作成・誤更新・削除の許可を確認した。
- [ ] VM・VNet・コンテナー・バックアップ・復元・削除に必要なRBACがある。Backup Contributorだけで全リソースを作成できるとは限らない。
- [ ] 元VM、事前復元VM、当日復元VMを配置できるvCPUクォータとVMサイズの容量を確認した。
- [ ] Azure VM Agent、バックアップ拡張機能、必要な送信通信が正常で、選択したVM構成がAzure Backupに対応している。
- [ ] 元VM・コンテナー・復元先・ステージング用ストレージは同じリージョンにそろえた。
- [ ] 元・復元先VNetは講師専用で、ASR環境や業務ネットワークへ接続していない。
- [ ] 両方のVNetでOS接続経路を用意した。Bastion Developerを使う場合はリージョンの対応を確認した。
- [ ] 検証用としてHTTP（TCP 80）のAny許可が承認されている。機密情報は配置せず、公開IPへのSSHは許可しない。
- [ ] Soft delete、イミュータビリティ、Resource Guard、組織ポリシー、保持期間による削除制約と、残存時の管理者を確認した。デモの都合で保護機能を無効化・強制解除しない。
- [ ] バックアップ・復元の待機上限と、事前復元VMに切り替える時点をリハーサルで決めた。

パスワードや秘密鍵は手順書・画面キャプチャへ記載しません。以降の`bash`コードは**Bastionなどで接続した対象Ubuntu VM内**で実行し、講師端末のPowerShellやCloud Shellでは実行しません。エラーが出たら原因を確認し、次の工程へ進みません。

## 4. 事前準備：HTML変更前・変更後の復旧ポイントを用意する

### 4.1 専用VMとネットワークを作成する

**Bicepで作成する場合**：[デプロイ手順](./infra/README.md)を実施し、出力の元VM・復元先VNet・Bastionなどを確認します。以下のPortal作成は不要です。Bicepには復元VM用の未関連付け公開IPとステージングストレージも含まれます。

1. Portalで専用RG、元VNet・サブネット・NSG、復元先VNet・サブネット・NSGを作成します。
2. 元VNetにUbuntu VMを作成し、承認済み経路からログインします。ASRは有効化しません。
3. 復元先サブネットには、元VMからの通信や業務宛て通信を許可しません。講師の接続と復元VMの運用に必要な通信だけ許可します。
4. OSログインとWeb確認の接続経路を用意します。公開IPを使う場合は演習専用とし、元・復元VMそれぞれのIPを区別します。

### 4.2 Apacheと正常なHTMLを構成する

Bicepでデプロイした場合も、この手順を元VM内で実行します。Apacheのインストールはインフラのデプロイと分離しているため、失敗時は表示されたエラーを解消し、該当コマンドを再実行します。復元VMでは実行しません。

既存の[Apache構成手順](../handson/iaas/exercises/02-configure-apache.md)と同じApache・自動起動のパターンを使用します。ただし、実行対象はこのデモ専用VMです。

```bash
sudo cloud-init status --wait
```

VMの初期設定完了を待ってから、パッケージをインストールします。エラーが出た場合は内容を確認してから進みます。

```bash
sudo apt-get update &&
sudo apt-get install -y apache2 curl
```

```bash
sudo apache2ctl configtest &&
sudo systemctl enable --now apache2 &&
systemctl is-enabled apache2 &&
systemctl is-active apache2
```

`Syntax OK`、`enabled`、`active`を確認します。正常なHTMLを配置します。この操作はデモ専用の既定ページを上書きします。

```bash
printf '%s\n' '<!doctype html>' '<html lang="en">' \
  '<head><meta charset="utf-8"><title>Azure Backup Demo</title></head>' \
  '<body><h1>Azure Backup Demo</h1>' \
  '<p>Recovery marker: backup-demo-good-v1</p></body></html>' \
  > /tmp/backup-demo-good.html &&
sudo install -m 644 /tmp/backup-demo-good.html /var/www/html/index.html &&
sync &&
sha256sum /var/www/html/index.html &&
date -u +%Y-%m-%dT%H:%M:%SZ
```

```bash
curl --fail --silent --show-error --connect-timeout 5 --max-time 15 http://127.0.0.1/
```

講師端末のブラウザーからも元VMを開き、`backup-demo-good-v1`を確認します。HTMLのSHA-256、書き込み完了UTC時刻、元VM名・リージョン・IPを**VM外のメモ**に控えます。

### 4.3 Azure Backupを有効化し、初回バックアップを完了する

Bicepでデプロイ済みなら、コンテナー・Enhancedポリシー・元VM保護は設定済みです。対象と設定を確認して、下の6「今すぐバックアップ」から実施します。日次の自動実行によるポイントが既にある場合も、正常HTMLを含むことを確認してから採用します。Bicepの完了は初回バックアップの完了ではありません。

1. 元VMと同じリージョンに、デモ専用のRecovery Servicesコンテナーを作成します。
2. コンテナーのプロパティで、バックアップのストレージ冗長性とセキュリティ設定を確認します。冗長性は保護開始前に確定します。
3. コンテナーの **バックアップ** から、実行場所 **Azure**、対象 **仮想マシン** を選択します。Portalの表示が異なる場合は、元VMの **バックアップ** またはResiliencyの保護画面から同じ対象を選びます。
4. 対応するEnhancedポリシーを作成・選択し、時刻・タイムゾーン、保持期間、Instant Restoreのスナップショット保持期間を記録します。正常な復旧ポイントが当日まで保持される設定にします。
5. デモ用の元VMだけを選び、バックアップを有効化します。
6. 対象のバックアップ項目で **今すぐバックアップ** を実行します。オンデマンドバックアップの保持期限も当日より後にします。
7. **バックアップジョブ** で対象・ジョブID・状態を確認し、初回バックアップが完了するまで待ちます。事前準備ではコンテナーへのデータ転送完了も確認します。
8. 復旧ポイント一覧に正常なHTMLを含むポイントが表示されることを確認し、ポイントの時刻・整合性の種類・利用可能な層を記録します。

**成功条件**：バックアップジョブ成功だけでなく、選択可能な復旧ポイントがあること。HTML配置より後、誤更新より前のポイントを選びます。Linuxのファイルシステム整合性を、任意のDBのアプリケーション整合性保証とは説明しません。

### 4.4 元VMのHTMLを変更し、変更後のポイントも取得する

変更前の初回バックアップ完了と復旧ポイントを確認してから、誤更新を想定した変更を行います。変更前のHTMLマーカー・SHA-256・復旧ポイント時刻はVM外に保存しておきます。

**元VMへ接続していることをPortalで確認**してから、デモ専用HTMLを上書きします。事前復元VMやASRのVMでは実行しません。

```bash
printf '%s\n' '<!doctype html>' '<html lang="en">' \
  '<head><meta charset="utf-8"><title>Azure Backup Demo</title></head>' \
  '<body><h1>Azure Backup Demo</h1>' \
  '<p>Recovery marker: backup-demo-bad-v2</p></body></html>' \
  > /tmp/backup-demo-bad.html &&
sudo install -m 644 /tmp/backup-demo-bad.html /var/www/html/index.html &&
sync &&
sha256sum /var/www/html/index.html &&
date -u +%Y-%m-%dT%H:%M:%SZ
```

```bash
curl --fail --silent --show-error --connect-timeout 5 --max-time 15 http://127.0.0.1/
```

ブラウザーでも`backup-demo-bad-v2`を確認します。変更UTC時刻とSHA-256をVM外に記録します。元VMの停止・削除は不要です。これは専用HTMLの変更であり、本番データを破壊する操作ではありません。

続けて **今すぐバックアップ** を実行し、変更後のバックアップジョブとコンテナーへのデータ転送が完了したこと、変更後の復旧ポイントが選択可能なことを確認します。両方のポイントの保持期限を確認し、次の対応表をVM外のメモに記録します。

| ポイント | バックアップ時点のHTML | 当日の扱い |
|---|---|---|
| 変更前 | `backup-demo-good-v1`と正常時のSHA-256 | 新しいVMへの復元元に選ぶ |
| 変更後 | `backup-demo-bad-v2`と変更後のSHA-256 | 最新でも目的の状態とは限らないことを説明 |

ポイント時刻とHTMLの対応は、バックアップを変更の前後で順番に完了させ、リハーサルで検証します。復旧ポイント一覧にHTMLの内容が表示されるわけではありません。

### 4.5 変更前のポイントから事前復元してリハーサルする

1. [当日の復元操作](#52-変更前の復旧ポイントから別vmを作成する)を、事前復元VM名で実施します。
2. [復元後の確認](#53-復元したvmのapacheとhtmlを確認する)を完了し、SHA-256が正常時と一致することを確認します。
3. 復元時間、接続経路、実際のPortalの項目、ジョブID、選択した復旧ポイントを記録します。
4. 事前復元VMは当日まで停止（割り当て解除）して保管し、デモ開始前に起動してHTTP応答を確認します。停止中もディスクなどの料金は残ります。
5. バックアップは元VMだけを対象にします。復元VMで自動的に保護されていないかも確認し、想定外の保護対象があれば設定と後片付けへの影響を確認します。
6. 元VMは変更後のHTMLのままにしておきます。当日使う変更前・変更後の復旧ポイントが保持されていることを再確認します。

## 5. 当日のデモ

### 5.1 現在のVMと復旧ポイントの履歴を見せる

1. Portalで講師用の元VM名・リージョン・IPと、Azure Backupが有効になっていることを示します。
2. 元VMのWebページを開き、現在は変更後の`backup-demo-bad-v2`が表示されていることを確認します。当日のHTML変更やバックアップ取得は不要です。
3. 復旧ポイント一覧で事前取得した変更前・変更後の時刻を示し、VM外の対応表と照合します。
4. 「最新のポイントには変更後の内容が入っています。今回は保持されている変更前のポイントを選び、元VMを上書きせず別VMとして取り出します」と説明します。
5. 任意の時刻ではなく、取得・保持されているポイントから選択することを補足します。

### 5.2 変更前の復旧ポイントから別VMを作成する

1. コンテナーの **バックアップ項目 → Azure仮想マシン → 元VM → VMの復元** を開きます。表示が異なる場合は **Resiliency → Recover** でDatasource typeに **Azure Virtual machines**、Protected itemに元VMを選びます。
2. 記録しておいた変更前の復旧ポイントを選びます。変更後のポイントも一覧にあることを示し、単に「最新」を選ばず、HTML変更前であることを確認します。
3. 復元構成で **新規作成（Create new）**、復元の種類で **新しい仮想マシンの作成（Create new virtual machine）** を選びます。**既存の置換（Replace existing）は使用しません。**
4. 当日復元VMの未使用の名前、デモ専用の復元先RG、同じリージョンの復元先VNet・サブネットを指定します。自動選択された先頭サブネットをそのまま採用せず、対象を確認します。
5. ステージング場所を求められた場合は、事前確認済みの専用ストレージアカウントを指定します。Bicep環境では出力の`stagingStorageAccountName`を使い、復元認証に**コンテナーのシステム割り当てマネージドID**を選びます。復元専用RGへのVM Restore Operatorのロール伝播も確認します。VMサイズ・ゾーン・セキュリティ設定などが表示される場合は、対応条件とリハーサル時の設定を確認します。
6. 元VMを上書きしないこと、ASR・業務ネットワークへ配置しないことを確認して復元を開始します。
7. 復元の開始UTC時刻、ジョブID、復旧ポイント、復元先を記録し、**バックアップジョブ** で進捗とエラーを確認します。

新規VM作成が選べない、またはジョブ失敗時にディスクだけが復元された場合は、本編の成功条件を満たしていません。エラー・対応条件を確認し、当日その場で別方式へ切り替えて成功扱いにしません。必要なら事前復元VMの結果確認へ切り替え、当日ジョブの状態を明示します。

### 5.3 復元したVMのApacheとHTMLを確認する

当日VMが完了していれば当日VM、待機上限に達していれば事前復元VMを使います。**どちらを見ているか、VM名とジョブを明示**します。

1. 復元ジョブの成功と、新しいVMリソースの作成・起動を別に確認します。
2. PortalでVM名・リージョン・VNet・IPを照合し、復元先NIC／サブネットのNSGを確認します。元VMの公開IPや接続経路がそのまま使えるとは扱いません。
3. リハーサルで決めたOS接続経路を使います。公開HTTPの場合は、復元先NICへ専用公開IPを関連付け、検証用としてTCP 80をAny許可にします。Bicep環境では事前／当日用に作成済みの公開IPと、HTTPをAny許可した復元先サブネットのNSGを使います。暗黙の送信アクセスは無効なため、公開IPを関連付けて送信経路を確保してから後続のVM拡張機能操作を行います。復元されたNSG設定も含め、HTTP以外に意図しない公開がないことを確認します。

   **Ubuntuのパスワード認証の注意**：復元後はパスワードがブロックされる場合があります。Bastion接続前に復元VMの **ヘルプ → パスワードのリセット** で既存管理者ユーザーのパスワードをVMAccess拡張機能で再設定し、成功を確認します。これは接続を再設定する操作で、Apache・HTMLは変更しません。必要なRBACと送信通信は事前に確認します。

4. 復元VMへログインし、以下を1ブロックずつ実行します。**Apacheの再インストールやHTMLの書き直しはしません。**

```bash
systemctl is-enabled apache2 &&
systemctl is-active apache2 &&
sha256sum /var/www/html/index.html
```

```bash
curl --fail --silent --show-error --connect-timeout 5 --max-time 15 http://127.0.0.1/
```

5. Apacheが`enabled`かつ`active`、HTMLが`backup-demo-good-v1`、SHA-256がVM外に控えた正常時の値と一致することを確認します。
6. 講師端末のブラウザーから復元VMのURLを開き、正常なHTMLを確認します。元VMのURLと並べ、元VMは`backup-demo-bad-v2`、復元VMは`backup-demo-good-v1`であることを示します。
7. HTTP確認の完了UTC時刻を記録します。ブラウザーのキャッシュが疑われる場合は再読み込みし、実際の接続先も照合します。

**説明例**：「誤更新後の元VMはそのままですが、過去の復旧ポイントから別VMにOS・Apache・HTMLを戻せました。業務へ戻すには、正しいデータの判断や接続先切り替えなど、さらに運用手順が必要です。」

## 6. 確認範囲とトラブル時の対応

| 状況 | 確認・対応 |
|---|---|
| バックアップ有効化済みだが復旧ポイントがない | 初回ジョブ・データ転送・エージェント・送信通信・保持期限を確認。誤更新へ進まない |
| 新しいVMへの復元が選べない／失敗 | VM構成の対応、権限、クォータ・容量、復旧ポイントの層、ネットワーク・ストレージの条件を確認 |
| 復元完了だがログイン・Web接続不可 | 復元先IP、Bastion、NIC／サブネットのNSG、ルート、OS Firewall、講師の接続経路を確認 |
| Ubuntuの復元後にパスワード接続できない | 公開IP等の送信経路とVM Agentを確認し、復元VMのVMAccess拡張機能で既存管理者ユーザーのパスワードを再設定する。ApacheやHTMLは作り直さない |
| Apacheが自動起動していない | 正常時の自動起動設定、選択ポイント、`sudo systemctl status apache2 --no-pager`とログを確認。再インストールして成功扱いにしない |
| 復元VMも誤更新後のHTMLになっている | ポイントの時刻、操作対象、HTML配置先を確認。正常なポイントから再実施し、HTMLを手で戻して成功扱いにしない |
| 事前復元VMへ切り替えた | 事前ジョブの結果と当日ジョブの状態を分けて説明・記録 |

- **ジョブ成功 ≠ 業務復旧**：VM起動、Apache稼働、ローカルHTTP、講師端末からのWeb表示を別に確認します。
- **今回の時間 ≠ 業務全体のRTO**：復元開始からHTTP確認までを測る場合も、検知・承認・DNS・認証・DBなどは含みません。事前復元VMの確認を当日ジョブの復元時間に合算しません。
- **正常HTMLの復元 ≠ RPOゼロ**：今回は過去の状態へ戻すため、その後の正当な更新も失われ得ます。ポイント時刻と誤更新時刻を照合し、戻す範囲を説明します。
- **ファイル一致 ≠ 全ディスク・業務データの完全性保証**：SHA-256で比較したのはこのHTMLだけです。

## 7. 終了後のクリーンアップ

講師が専用リソースの名前・RG・保護対象を照合し、削除承認を確認して実施します。共有コンテナーや参加者のASR環境は操作しません。

1. 当日復元ジョブが実行中なら結果と作成リソースを確認してから片付けます。失敗時も、ディスク・NIC・ステージングのVHDなどが残っていないか確認します。
2. バックアップ項目一覧を確認し、デモ専用VMの保護を **バックアップの停止 → バックアップデータの削除** で終了します。復元VMも保護されていた場合は、その項目も対象確認の上で対応します。「データを保持して停止」だけではデータは残ります。
3. Soft deleteに入った項目は設定された期間残り、コンテナーの削除を妨げる場合があります。イミュータビリティなどで削除できない場合も、保護設定を強制解除しません。残存理由・期限・管理者・後日削除日を記録します。
4. バックアップ・復元に必要な処理が終了したことを確認して、元・事前復元・当日復元の専用VMを削除します。関連ディスク・NIC・公開IPが自動削除されたかも個別に確認します。
5. ステージング用ストレージの専用VHD・コンテナー、残存スナップショット、専用Bastion、VNet・NSGなどを確認し、不要なデモ専用リソースを削除します。
6. 保護項目・Soft delete中のデータなどの依存関係がなくなってからRecovery Servicesコンテナー、空の専用RGを削除します。RGごとの一括削除を最初の操作にしません。
7. 削除できなかったものは残存リソースとして管理し、料金の発生有無を確認します。VM停止やVM削除だけで環境全体の課金が終了したとは説明しません。

## 8. 講師用の完了チェック

- [ ] HTML変更前・変更後の復旧ポイントを事前に取得し、時刻・HTMLマーカー・SHA-256の対応を記録した。
- [ ] 同じポイントから事前VMへ復元し、OS接続・Apache・HTMLのSHA-256・ブラウザー表示を確認した。
- [ ] 当日は準備済みの元VMとポイント履歴を示し、任意の時刻ではなく保持されたポイントから選ぶことを説明した。
- [ ] 当日ジョブの対象・復旧ポイント・復元先・結果を記録した。
- [ ] 当日VMと事前VMを混同せず、結果確認に使ったVMを明示した。
- [ ] 元VMの誤更新HTMLと復元VMの正常HTMLを比較した。
- [ ] デモの検証範囲・未完了部分を説明した。
- [ ] クリーンアップと残存リソースの管理担当・期限を確認した。
