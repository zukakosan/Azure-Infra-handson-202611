# PaaS：Azure SQL DatabaseによるDRハンズオン

> 叩き台。PaaSの代表例としてAzure SQL DatabaseのFailover Groupを使用します。実施リージョン、サービス階層、認証・接続方法、Portal画面は事前リハーサルで確定してください。展開用IaCと業務アプリの実装は本資料に含みません。

## 1. 目的とシナリオ

Region AのAzure SQL DatabaseからRegion Bへデータを複製し、Failover Groupで書き込み先を切り替えます。切り替え後も同じ読み取り／書き込みリスナーを使い、登録済みデータの参照と新しいデータの登録を確認します。

基本演習は、**両リージョンが利用可能な状態での計画フェールオーバー**です。実際のリージョン障害やデータ損失の可能性がある強制フェールオーバーは起こしません。

### 到達目標

- Primary／Secondary、複製、Failover Groupの役割を説明できる。
- サーバー個別の接続先と、役割変更に追従するリスナーを区別できる。
- 計画フェールオーバー後に同じ接続先で再接続し、データを読み書きできる。
- 元のリージョンへ戻した後も、切り替え先で登録したデータを確認できる。
- 計画切り替えの結果と、実障害時のRTO／RPOを区別できる。

### 今回の対象範囲

| 対象 | 扱い |
|---|---|
| Azure SQL Databaseのリージョン間複製 | 事前構築済みの設定と正常性を確認 |
| Failover Groupの計画フェールオーバー | 参加者が操作 |
| 同じリスナーへの再接続、データの読み書き | SQLクライアントで確認 |
| 元のリージョンへの計画フェールバック | データと複製を確認して実施 |
| 強制切り替え、自動切り替え、実リージョン障害 | 基本演習では実行しない |
| Webアプリ、Front Door、セッション、外部依存 | 対象外。別途復旧が必要なものとして整理 |
| 誤削除・誤更新からのバックアップ復元 | 対象外 |

PaaS全般に同じDR機能があるわけではありません。本演習の結果をStorage、Cosmos DB、App Serviceなどの保証として扱いません。

## 2. 構成

```text
参加者のSQLクライアント
       │
       └─ 読み取り／書き込みリスナー
          <Failover Group名>.database.windows.net
                         │
                 現在のPrimaryへ接続

Region A                                  Region B
論理サーバーA                             論理サーバーB
  └─ 演習DB（Primary） ── 非同期複製 ──>    └─ 演習DB（Secondary）

計画フェールオーバー後：
サーバーBがPrimary、サーバーAがSecondaryとなり、複製方向も変わる
リスナー名は変更せず、クライアントは接続を再確立する
```

リスナーは既存セッションを無停止で移動する仕組みではありません。切り替え時には接続切断が起こり得るため、再接続・再試行の設計が必要です。

## 3. 所要時間

Failover Groupの作成と初期複製が完了した状態で、約50分を想定します。切り替え・DNS反映・接続再確立の時間は保証されません。

| 所要 | 内容 |
|---|---|
| 10分 | 構成・接続先・複製状態の確認 |
| 5分 | 切り替え前のデータ登録 |
| 15分 | 計画フェールオーバーと再接続・読み書き |
| 10分 | 計画フェールバックとデータ確認 |
| 10分 | 記録、後片付け、振り返り |

## 4. 事前準備

### 4.1 講師・環境管理者

- [ ] 参加者またはグループごとに専用の演習DBとFailover Groupを用意する。共有グループを複数人が同時に切り替えない。
- [ ] 同じMicrosoft Entraテナント内の異なるリージョンに、論理サーバーA・Bを用意する。
- [ ] 演習DBに対応したサービス階層・サイズを両系に用意し、容量と費用を確認する。
- [ ] サーバーAでFailover Groupを作成し、パートナーにサーバーB、対象に演習DBを指定する。
- [ ] 初期複製が完了し、両系が正常で、計画フェールオーバーが可能な状態にする。
- [ ] 演習中に意図しない切り替えが起きないよう、顧客管理／手動の切り替え方針を設定する。画面上の表記と設定値をリハーサルで確認する。
- [ ] 両論理サーバーでMicrosoft Entra認証の設定と必要なDB権限を用意する。
- [ ] SQL Server Contributorなど、切り替えに必要なAzure RBACを両サーバーの対象スコープに付与する。DB内のSELECT／INSERT権限は別に付与する。
- [ ] 両リージョンへのネットワーク経路、名前解決、接続許可を用意する。Private Endpoint利用時は両系のDNSと経路を検証する。
- [ ] 公開エンドポイントを使用する場合は承認済み接続元だけを許可する。接続確認のためにFirewallを全開放しない。
- [ ] SSMSなど、リスナー名を指定しMicrosoft Entra認証で接続できるSQLクライアントを用意する。
- [ ] 次の演習用テーブルを初期Primaryの演習DBで一度だけ作成する。参加者にはテーブル作成権限を必須としない。
- [ ] サーバーBへの切り替え、同じリスナーからの再接続、元への復帰までリハーサルする。

```sql
CREATE TABLE dbo.DrExerciseRecords
(
    RecordId uniqueidentifier NOT NULL
        CONSTRAINT PK_DrExerciseRecords PRIMARY KEY,
    ExerciseKey nvarchar(100) NOT NULL,
    Phase nvarchar(30) NOT NULL,
    CreatedAtUtc datetime2(3) NOT NULL
        CONSTRAINT DF_DrExerciseRecords_CreatedAtUtc DEFAULT SYSUTCDATETIME()
);
```

本資料のSQLは専用の演習DBだけで実行します。実データ、個人情報、資格情報を登録しません。
