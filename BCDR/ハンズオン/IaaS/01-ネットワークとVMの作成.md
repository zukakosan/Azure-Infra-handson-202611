## このページの手順

### Step 1：PortalでネットワークとUbuntu VMを作成する

#### 1.1 名前・リージョンとリソースグループ

`<演習ID>`は参加者・グループごとに決める英数字の乱数（例：`a7k3p9`）へ置き換え、すべてのリソース名で共通使用します。`bcdr`などの用途名は各リソース名に含まれるため、演習IDには重ねて含めません。

| リソース | 名前例 | 配置 |
|---|---|---|
| 元の環境用リソースグループ | `rg-bcdr-src-<演習ID>` | Region A |
| 通常復旧先・コンテナー用リソースグループ | `rg-bcdr-dr-<演習ID>` | Region B |
| テスト用リソースグループ | `rg-bcdr-test-<演習ID>` | Region B |
| 元のVNet／サブネット | `vnet-bcdr-src-<演習ID>`／`subnet-web` | Region A |
| 通常復旧先VNet／サブネット | `vnet-bcdr-dr-<演習ID>`／`subnet-web` | Region B |
| テスト専用VNet／サブネット | `vnet-bcdr-test-<演習ID>`／`subnet-web` | Region B |
| 元のVM | `vm-bcdr-src-<演習ID>` | Region A |
| 元／テスト用NSG | `nsg-bcdr-src-<演習ID>`／`nsg-bcdr-test-<演習ID>` | 各リージョン |
| 通常復旧先NSG | `nsg-bcdr-dr-<演習ID>` | Region B |
| 各VNetのBastion Developer | `bas-bcdr-src-<演習ID>`／`bas-bcdr-dr-<演習ID>`／`bas-bcdr-test-<演習ID>` | 各VNetと同じリージョン |
| Recovery Servicesコンテナー | `rsv-bcdr-<演習ID>` | Region B |

1. Portalで **リソースグループ → 作成** を開き、元環境用、DR用、テスト用の3つのグループを作成します。
2. サブスクリプションと名前を確認します。リソースグループの所在地だけで、配下のリソースのリージョンが決まるわけではありません。
3. グループ内に既存の共有・本番リソースがないことを確認します。

#### 1.2 VNetとサブネットを作成する

**仮想ネットワーク → 作成** で、次の3つを作成します。アドレス範囲は演習例であり、既存接続がある場合は重複しない値を選びます。

| VNet | アドレス空間 | `subnet-web` |
|---|---|---|
| 元のVNet | `10.10.0.0/16` | `10.10.1.0/24` |
| 通常復旧先VNet | `10.20.0.0/16` | `10.20.1.0/24` |
| テスト専用VNet | `10.30.0.0/16` | `10.30.1.0/24` |

元のVNetは元のグループ・Region A、通常復旧先VNetとコンテナーは復旧先グループ・Region B、テスト用VNetはテスト用グループ・Region Bに作成します。本演習ではVNetピアリング、オンプレミス接続、本番経路、Firewallを設定しません。各VNetにBastion Developerを用意します。

#### 1.3 Bastion経由のSSHと演習用HTTPのNSGを作成する

1. **ネットワークセキュリティグループ → 作成** で、元用NSG・通常復旧先NSG・テスト用NSGをそれぞれのリージョンに作成します。
2. 3つのNSGの **受信セキュリティ規則 → 追加** で、次の規則を作成します。

| 規則 | 優先度 | ソース | 宛先 | プロトコル／宛先ポート | 操作 |
|---|---|---|---|---|---|
| `Allow-Ssh-From-VirtualNetwork` | 100 | Service Tag：VirtualNetwork | Any | TCP／22 | Allow |
| `Allow-Ssh-From-Platform` | 110 | IP Addresses：`168.63.129.16/32` | Any | TCP／22 | Allow |
| `Allow-Http-For-Lab` | 120 | Any | Any | TCP／80 | Allow |
| `Deny-Other-Ssh` | 130 | Any | Any | TCP／22 | Deny |

送信元ポートは`*`を使用します。SSHはVNet内・プラットフォーム経路に限定し、その他からは拒否します。HTTP（80）だけは演習の静的ページ確認用にAnyへ許可します。暗号化・認証はなく世界中から閲覧できるため、機密値・個人情報を置かず、終了後に削除します。HTTPS（443）は構成しません。

3. 元用NSGを元のVNet、通常復旧先NSGを通常復旧先VNet、テスト用NSGをテスト専用VNetの各`subnet-web`へ関連付けます。
4. 既定の受信拒否規則を残し、ASRとパッケージ取得に必要な送信通信を妨げる規則がないことを確認します。

テストVNetは本番から分離しますが、公開IPを後で関連付けるため「外部通信が完全に遮断された環境」ではありません。本演習の静的HTML以外に本番データ、DB接続設定、自動送信処理を持ち込みません。

#### 1.4 Ubuntu VMを作成する

1. **仮想マシン → 作成 → Azure仮想マシン** を開きます。
2. **基本** タブで以下を設定します。

| 項目 | 設定 |
|---|---|
| リソースグループ／リージョン | 元のグループ／Region A |
| VM名 | `vm-bcdr-src-<演習ID>` |
| 可用性オプション | インフラストラクチャ冗長性は必要ありません（演習用） |
| セキュリティの種類 | トラステッド起動の仮想マシン（Trusted Launch）。Secure BootとvTPMを有効 |
| イメージ | 標準のUbuntu Server 22.04 LTS - Gen2 |
| サイズ | 両リージョンで利用できるサイズ。例：`Standard_D2s_v5` |
| 認証の種類／ユーザー名 | パスワード／`azureuser` |
| パスワード | `<演習用パスワード>`（講師から別途受け取る。他の環境・アカウントでは絶対に使用しない） |
| パブリック受信ポート | なし。[Step 1.3](./01-ネットワークとVMの作成.md)のサブネットNSGで必要な通信だけを許可 |

イメージ名だけでASR対応を断定せず、実際のOS・カーネルを確認します。[Trusted LaunchのASR対応条件](https://learn.microsoft.com/ja-jp/azure/site-recovery/concepts-trusted-vm)ではUbuntu 22.04をサポートし、Linux VMは2024年4月1日より後に作成されたものが対象です。本演習は新規作成・共有ディスクなしのAzure-to-Azure構成です。対応するGen2イメージとVMサイズを選び、エラーを回避するためにSecure Boot・vTPMを無断で無効にしません。

LinuxのTrusted Launch VMでは、VM作成画面の **管理 → Site Recovery** を有効にせず、作成後に[03のコンテナーからの手順](./03-ASRの構成と初期複製.md)で複製を有効化します。ブート整合性監視の状態はASRで複製されないため、本演習の検証対象には含めません。

3. **ディスク** で標準SSDなどの永続的なOS管理ディスクを選択します。エフェメラルOSディスクは使用せず、追加データディスクは作成しません。
4. **ネットワーク** で元のVNet・`subnet-web`を選択し、演習専用のStandard SKUの公開IPv4を新規作成します。IP名を記録します。
5. NIC側のNSGは「なし」とし、サブネットに元用NSGが関連付いていることを確認します。NICにもNSGがある場合は、両方で1.3と同じSSH・HTTP規則が適用されることを確認します。
6. **詳細** のカスタムデータは空欄にし、cloud-initによるアプリ設定を行いません。カスタムイメージも使用しません。
7. **確認および作成** で対象、価格、公開IP、ネットワークを確認して作成します。
8. 展開完了後、VMのリージョン、稼働状態、公開IP、ディスク、NSGの関連付けを確認します。VMの **構成** または **プロパティ** でTrusted Launch、Secure Boot・vTPMの有効状態も記録します。
9. 各VNetの **接続 → Bastion** を開き、**Developer** を選びます。Developerでは初回の接続時にBastionが自動配置されます。手動で作成する場合もSKUをDeveloperにし、名前を上表の例として記録します。`AzureBastionSubnet`とBastion専用公開IPは不要です。復旧先・テスト用VNetではVM復旧後の初回接続時に同じ操作を行います。Developerが利用できない場合は停止して講師に相談します。既定の「Bastionのデプロイ」で有料のStandardを作成しないでください。
10. 元VMの **接続 → Bastion** を開き、DeveloperのBastionで、認証を **パスワード**、ユーザー名を`azureuser`、パスワードを講師から受け取った演習用パスワードとして接続し、ブラウザー内のターミナルを開きます。他の環境・アカウントでは絶対に使用しません。
11. 接続先VM名とプライベートIPを確認します。公開IPへのネイティブSSH接続は使用しません。Developerは同時に1接続のため、別VMへ移る前にセッションを閉じます。

**確認結果**：Region Aに専用Ubuntu VMが作成され、Bastion Developer経由でパスワードログインできること。Region Bではネットワークを用意し、復旧用VMを手動で作成しません。手動構築時のRegion BのBastion Developerは復旧VMへの初回接続時に配置します。Bicep利用時は3つとも作成済みです。

公開IPは元VMの明示的な送信経路にも使用します。新規VNetの既定の送信接続だけに依存せず、パッケージ配布先・ASRに必要な宛先へ実際に接続できることを確認します。SSHや送信通信が失敗する場合は記録し、許可範囲を全開放して回避しません。

- [ ] 元のUbuntu VMと公開IPを作成し、Bastion Developer経由でパスワードログインできた。
