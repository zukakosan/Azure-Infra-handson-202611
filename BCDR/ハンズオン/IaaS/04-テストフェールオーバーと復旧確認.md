# IaaS 04：テストフェールオーバーと復旧確認

[前へ](./03-ASRの構成と初期複製.md) | [全体・進捗チェック](../01-IaaS-ASRによるDRハンズオン.md) | [次へ](./05-実フェールオーバーとHTML更新.md)

> 現在位置：4 / 9。このページの到達点：テスト用VMで復旧を確認し、テストを終了して実切り替えに進める。

[前のページ](./03-ASRの構成と初期複製.md)の完了条件を満たしてから進んでください。

時刻・証拠・未取得項目は[観測記録](./09-観測記録と振り返り.md)へ随時記入します。

## このページの手順

### Step 4：テストフェールオーバーを実行する

1. 対象のレプリケートされたアイテムで **テストフェールオーバー（Test Failover）** を選択します。通常の **フェールオーバー** は選択しません。
2. 基本演習では **最新の処理済み（Latest processed）** を選び、表示された復旧ポイントの時刻を記録します。[Step 3](./03-ASRの構成と初期複製.md)で確認した構成後の時刻であることを再確認します。
3. Region Bの指定された **テスト用VNet** を選択します。元の業務ネットワークは選択しません。
4. 対象、復旧ポイント、接続先を作業者と承認者で確認します。
5. 実行し、操作開始時刻を記録します。
6. **Site Recoveryジョブ（Site Recovery jobs）** で進行状況を確認し、ジョブID、各工程、完了または失敗の状態を記録します。

**確認結果**：テストフェールオーバージョブが成功し、Region Bにテスト用VMが作成されること。

待機上限を超えた場合や失敗した場合は、ジョブのエラーを保存して講師へ連絡します。原因を確認せずに同じ操作を繰り返したり、通常のフェールオーバーで代替したりしません。

### Step 5：復旧先のApache・HTML・通信経路を確認する

#### 5.1 OSとファイルの復旧を確認する

1. Portalでテスト用VMのリージョン、稼働状態、VMサイズ、接続先VNet・IPアドレスを確認します。Trusted Launch、Secure Boot・vTPMの有効状態も元VMと照合します。ブート整合性監視の状態は複製されません。
   ASRが作成したテストVMのRGは固定と仮定せず、Portalで実際の配置先を記録します。テスト用ネットワーク自体は`rg-bcdr-test-<演習ID>`にあります。
2. テスト用VMの **ネットワーク設定** から実際のNICを開き、テスト専用VNet・`subnet-web`に接続していることを確認します。
3. NICの **IP構成** で主IP構成を開き、Region Bの演習専用Standard SKUの公開IPv4を新規作成して関連付けます。元VMの公開IPが自動で引き継がれるとは仮定しません。新規作成の導線がない場合は、Portalの **パブリックIPアドレス → 作成** で作成してから選択します。
4. テスト用NSGがサブネットに関連付いていることと、NICにもNSGがある場合の実効規則を確認します。[Step 1.3](./01-ネットワークとVMの作成.md)と同じBastion経由のSSH許可・その他SSH拒否・HTTP（80）のAny許可を確認し、公開IPと関連リソース名を記録します。
5. **テスト用VM**の **接続 → Bastion** から、テスト専用VNetのBastion Developerと、`azureuser`・講師から受け取った演習用パスワードで接続します。元VMのBastionセッションを閉じ、接続先VM名・プライベートIPを確認します。公開IPはHTTP確認専用で、SSHの接続先にはしません。
6. 次のコマンドでApacheとHTMLを確認します。復旧先でインストールやページ配置をやり直しません。

```bash
systemctl is-enabled apache2 &&
systemctl is-active apache2 &&
cat /var/www/html/index.html &&
curl --fail --silent --show-error --connect-timeout 5 --max-time 15 http://127.0.0.1/
```

**確認結果**：Apacheが自動起動し、演習ID・メッセージが元の記録と一致すること。

#### 5.2 利用者の接続経路から表示を確認する

1. 参加者のブラウザーで`http://<テスト用VMの公開IP>/`を開きます。
2. 元のURLではなくテスト用VMのURLであることを確認し、演習ID・メッセージを照合します。キャッシュが疑わしい場合は強制再読み込みと実リクエストを確認します。
3. 5秒以上の間隔で3回連続して正常表示を確認し、時刻と確認場所を記録します。
4. 元のVMのページも引き続き表示できることを確認します。

**確認結果**：VM内のローカルHTTPだけでなく、指定の利用者経路からも復旧先ページが利用できること。

#### 5.3 テスト環境が独立していることを確認する

元と復旧先のHTML一致を記録した**後**、テスト用VMだけで確認用コメントを追加します。ブラウザーの表示本文は変わりません。

```bash
(
  set -eu
  printf '\n<!-- test-vm-only: %s -->\n' "$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
    | sudo tee -a /var/www/html/index.html
  sync
  cat /var/www/html/index.html
)
```

元のVMへ別途ログインし、`cat /var/www/html/index.html`で`test-vm-only`コメントが追加されていないことを確認します。

**確認結果**：テスト用VMだけでファイルが変わり、元のVMへ同期されていないこと。これはファイルの変更確認であり、Web経由のデータ登録やDBの書き込み試験ではありません。

テスト側だけの変更は元へ戻されず、クリーンアップで失われます。

### Step 6：テストフェールオーバーを終了する

1. 必要な証拠とテスト側だけの変更記録をVM外へ保存します。
2. レプリケートされたアイテムで **テストフェールオーバーのクリーンアップ（Cleanup test failover）** を実行し、テスト結果を記入します。
3. クリーンアップジョブの成功とテスト用VMの削除を確認します。手動作成したテスト用公開IPなどが残る場合は、その所在を記録します。
4. 元のVM・Webページ・AからBへの複製が正常であることを確認します。

**確認結果**：テストが終了し、実フェールオーバーへ進めること。この時点では、元のVM、コンテナー、複製設定、通常復旧先VNetを削除しません。

テスト用VMの削除はフェールバックではありません。次のページで元VMを停止し、通常復旧先VNetへ実際に切り替えます。

## このページの完了チェック

- [ ] テスト用VNetへテストフェールオーバーし、接続経路を設定した。
- [ ] 復旧先でApacheが起動し、HTMLの演習ID・メッセージが元と一致することを確認した。
- [ ] 利用者経路から3回連続で表示し、テスト側の変更が元へ戻らないことを確認した。
- [ ] テストをクリーンアップし、元の環境と複製の正常性を確認した。
