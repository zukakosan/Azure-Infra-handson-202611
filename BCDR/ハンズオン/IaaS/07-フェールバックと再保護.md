# IaaS 07：フェールバックと再保護

[前へ](./06-逆方向の再保護.md) | [全体・進捗チェック](../01-IaaS-ASRによるDRハンズオン.md) | [次へ](./08-クリーンアップ.md)

> 現在位置：7 / 9。このページの到達点：更新したHTMLを保持してAへ戻り、AからBの保護を再確立できる。

[前のページ](./06-逆方向の再保護.md)でBからAへの再保護と複製が正常であることを確認してから進みます。単にRegion Aの古いVMを起動する手順ではありません。

時刻・証拠・未取得項目は[観測記録](./09-観測記録と振り返り.md)へ記入します。

## このページの手順

### Step 10：Region BからAへフェールバックする

#### 10.1 戻す条件を確認し、Region Bを停止する

1. Region Aの容量・権限・ネットワークが正常で、BからAの複製が正常であることを確認します。
2. BのHTMLをこれ以上変更せず、[更新時の記録](./05-実フェールオーバーとHTML更新.md)と現在のマーカーが一致することを確認します。
3. BのHTML更新後の復旧ポイントがあることと、Aで確認するマーカーを承認者と確認します。
4. 戻す先が元のVNet・グループであることを確認し、利用者影響を承認してから、Bの**現在稼働中の復旧VM内**で次を実行します。

```bash
sync &&
sudo shutdown -h now
```

5. SSH接続が切断されます。PortalでBのVMが停止状態であることと、Bの公開IPへの新しいHTTP要求が失敗することを確認し、時刻を記録します。OS内からの停止なので「停止（割り当て解除）」になるとは限りません。

再保護後のBにはRead-onlyロックがある場合があるため、停止はOS内から行います。Portalで拒否された操作を通すためにロックを削除しません。SSH切断だけでは停止完了の証拠になりません。

**確認結果**：Bが停止し、更新後HTMLの復旧ポイントと照合基準があること。停止が確認できない場合は、両系稼働を避けるためフェールバックを実行せず講師へ連絡します。

#### 10.2 Aへフェールオーバーし、更新後HTMLを確認する

1. 対象のレプリケートされたアイテムで **フェールオーバー（Failover）** を選択します。BからAへの逆方向のフェールオーバーが、今回のフェールバックです。
2. ソースB、ターゲットAと元のネットワークを確認し、**最新（Latest）**を選択します。Bで更新後のデータが複製されているという前提を省略しません。
3. **開始前にマシンをシャットダウンする** が表示される場合は選択します。これは失敗時も続行され得るため、先に行ったOS停止と状態確認を代替しません。
4. 実行時刻とSite Recoveryジョブの結果を記録します。
5. 復帰したAのVM・ディスク・NIC・VNetをPortalで確認します。Trusted Launch、Secure Boot・vTPMの有効状態も照合します。元のVM名やIP、NICが必ずそのまま再利用されるとは仮定しません。
6. Aの実際のNICの主IP構成を確認し、必要に応じて演習専用Standard公開IPv4を関連付けます。未関連付けの元の公開IPを再利用する場合も、リージョン・SKU・対象NICを確認します。
7. 元用NSGと、NICにもNSGがある場合の実効規則で、[Step 1.3](./01-ネットワークとVMの作成.md)と同じBastion経由のSSH許可・その他SSH拒否・HTTP（80）のAny許可があることを確認します。
8. 復帰したAのVMの **接続 → Bastion** から元VNetのBastion Developer経由で、`azureuser`と講師から受け取った演習用パスワードを使って接続し、次を実行します。HTMLを書き直したり、Apacheを再インストールしたりしません。

```bash
systemctl is-enabled apache2 &&
systemctl is-active apache2 &&
cat /var/www/html/index.html &&
curl --fail --silent --show-error --connect-timeout 5 --max-time 15 http://127.0.0.1/
```

9. **Bで更新後に記録したマーカー`apache-html-updated-in-region-b`が表示されること**を確認します。初期構築時の表示に戻ることを成功条件にしません。
10. ブラウザーでAの公開IPへ接続し、5秒以上の間隔で3回連続して正常表示を確認します。最初の成功と連続確認完了の時刻を記録します。
11. Bが停止したままであることを確認します。

**確認結果**：Aへ戻したVMで、Bで更新したHTMLが保持されていること。AとBの両方を稼働させたり、AでHTMLを再作成して一致を装ったりしません。

ジョブ失敗やマーカー不一致の場合はコミットせず、現在の稼働先・データ・証拠を保存して講師へ連絡します。Bの再起動や保護無効化を独断で行いません。

#### 10.3 戻した結果をコミットする

1. AのWeb表示、更新後マーカーの一致、Bの停止を承認者と確認します。
2. **コミット（Commit）** を実行し、ジョブ成功と**Failover committed**に相当する状態を確認します。
3. コミットにより既存の復旧ポイントが削除されることを確認し、証拠を先に保存します。

### Step 11：Region AからBへの保護を再確立する

1. Aへのフェールバックがコミット済みであること、AのWebが正常であることを確認します。Aの公開IP・NSGなどの接続設定は再保護を開始する前に確定します。
2. **再保護（Re-Protect）** を選び、ソースA、ターゲットB、通常復旧先のグループ・VNet・サブネット・VMサイズを確認します。テスト専用VNetは指定しません。
3. [逆方向の再保護](./06-逆方向の再保護.md)と同様に、キャッシュストレージが稼働先のAに必要なことと、Bの旧復旧VM・ディスクが再構成され得ることを承認します。BのVMやディスクを先に手動削除しません。
4. 再保護を実行し、Site Recoveryジョブと複製状態を確認します。
5. 完了後、Aが稼働先で、AからBの複製が正常で、更新後HTMLを含む復旧ポイントがあることを確認します。
6. AのWeb表示とマーカーが変わっていないことを確認し、終了時の保護状態を記録します。Bの旧復旧VMは手動起動しません。

**確認結果**：元の稼働リージョンに戻るだけでなく、AからBへ再び保護できる状態になったこと。再保護が未完了の場合は「Aで稼働再開、DR保護再確立は未完了」と記録し、本ページを完了扱いにしません。
