## 6. 観測記録

時刻はUTCなど同じタイムゾーンに統一します。ログのイベント時刻と画面で確認した時刻を区別し、取得できなかった値は「未取得」とします。

| 項目 | 記入欄 |
|---|---|
| 対象VM／復旧先／テスト用VNet |  |
| 作成したグループ／ASR自動作成リソースの所在 |  |
| ASR有効化開始／初期複製完了／待機時間 |  |
| 選択した復旧ポイントの種類・時刻 |  |
| HTMLマーカー／Write completed at UTC |  |
| 元と復旧先のHTMLマーカーの一致（変更前） |  |
| 元と復旧先のHTTP URL／確認場所・接続経路 |  |
| t0：テストフェールオーバー操作開始 |  |
| t1：ジョブ完了 |  |
| t2：利用者経路から復旧先ページの最初の正常表示 |  |
| t3：HTML照合と3回連続表示確認の完了 |  |
| t1－t0／t3－t0 |  |
| クリーンアップ結果／元の環境・複製の正常性 |  |
| 演習環境の最終削除結果／残存リソース・確認担当 |  |
| エラー、証拠への参照、未確認事項 |  |

`t3－t0`は、今回の条件での**テスト操作開始からWebページの検証完了までの時間**です。実障害の検知、承認、本番経路変更、外部依存先は含まず、業務全体のRTOではありません。

復旧ポイント時刻と操作開始時刻の差はデータの鮮度を考える材料ですが、それだけで業務RPOを実測したことにはなりません。配置したHTMLマーカーの保持を報告し、継続的な業務データ書き込みと実障害時の損失上限は未検証とします。

### 実フェールオーバー・再保護・フェールバックの記録

| 項目 | 記入欄 |
|---|---|
| Region Aの停止開始／停止確認／最初のHTTP失敗 |  |
| AからBへのフェールオーバー開始／ジョブ成功 |  |
| Bの利用者経路から最初の成功／3回連続確認完了 |  |
| AからBで選択した復旧ポイント／コミット結果 |  |
| BのVM・VNet・公開IP／Aが停止している根拠 |  |
| Bで更新後のHTMLマーカー・Write completed at UTC |  |
| BからAへの再保護開始／完了／複製正常性 |  |
| Bの更新後に生成された復旧ポイントの時刻 |  |
| Bの書き込み停止・OS停止確認／最初のHTTP失敗 |  |
| BからAへのフェールバック開始／ジョブ成功 |  |
| Aの最初のHTTP成功／3回連続確認完了 |  |
| Aへ戻す際の復旧ポイント／コミット結果 |  |
| Aで確認した更新マーカー／Bの記録との一致 |  |
| 復帰後のVM・公開IP／Bが停止している根拠 |  |
| AからBへの再保護開始／完了／複製正常性 |  |
| 停止から安定したWeb表示までの時間（往路／復路） |  |
| 再保護・複製待ち時間／承認・手作業の時間 |  |
| 終了時の稼働リージョン／保護状態／未完了工程 |  |

VM停止から指定した利用者経路での3回連続表示までを、今回のWeb復旧時間として報告します。停止操作の開始時刻と停止確認時刻、最初のHTTP失敗を区別し、比較に使った起点を明記します。本番DNS、認証、DB、外部依存、全利用者の復旧は未検証です。

フェールバック後のマーカー一致は、演習で更新した表示内容が戻ったことの証拠です。ファイル全体の完全一致、ASRの非同期複製全般のRPOゼロ、実リージョン障害時のデータ損失ゼロを保証するものではありません。

## 7. よくある問題と中止条件

| 状況 | 確認・対応 |
|---|---|
| パッケージの更新・インストールに失敗 | VMの送信通信、名前解決、配布先、パッケージ管理のエラーを確認。エラーを保存し、成功を確認してから進む |
| 復旧ポイントがない／複製異常 | 初期複製、エージェント、必要な送信通信、キャッシュストレージを講師と確認 |
| VM作成に失敗 | ジョブの詳細、権限、クォータ、VMサイズの容量、ネットワーク設定を確認 |
| VMは起動したが接続できない | テスト用IP、NSG、ルート、Bastionなどの接続経路を確認 |
| Apacheが起動しない | `sudo apache2ctl configtest`、`sudo systemctl status apache2 --no-pager`、`sudo journalctl -u apache2 --no-pager -n 50`で確認 |
| VM内のcurlは成功、ブラウザーは失敗 | 対象IP、TCP 80のNSG・OS Firewall、ルート、参加者のHTTP接続経路を確認。Bastionログイン成功とHTTP到達を区別 |
| HTMLが既定ページ／内容不一致 | 更新後の復旧ポイント、保存先ディスク、対象VM、ブラウザーキャッシュを確認。復旧先で上書きして成功扱いにしない |
| テスト用VMが本番へ通信している | 演習を中止し、講師の指示でテストVMを停止・隔離する。証拠を保存して影響を確認 |
| 再保護が選択できない | フェールオーバーのコミット状態、戻す先のリージョン・権限・リソース、ジョブの状態を確認 |
| 再保護が完了しない／更新後の復旧ポイントがない | ジョブ詳細、キャッシュストレージ、送信通信、容量を確認。フェールバックへ進まず、現在の稼働先と未保護状態を記録 |
| VMの操作がRead-onlyロックで拒否される | ASRの保護状態を確認し、ロックを手動解除して回避しない。フェールバック前のBの停止はOS内から行う |
| 両リージョンのWebが同時に稼働 | 演習を中止し、現在の正しいファイルと稼働先を確定する。無条件に元VMを起動しない |
| フェールバック後のマーカー不一致 | Bで記録したマーカー、更新後の復旧ポイント、戻したVMを確認。Aで同じHTMLを作り直して成功扱いにしない |

## 8. 完了条件と振り返り

- [ ] Ubuntuへログインし、Apacheのインストールと自動起動を設定した。
- [ ] 当日PortalでVM・ネットワーク・コンテナーを作成し、ASRを有効化した。
- [ ] HTMLを配置し、表示を確認してHTMLマーカーと時刻を記録した。
- [ ] HTML構成後の復旧ポイントと復旧先構成を確認した。
- [ ] 隔離ネットワークでテスト用VMを起動した。
- [ ] 復旧先で再構成せずにApacheが起動し、HTMLマーカーが一致した。
- [ ] 利用者経路からのページ表示を確認した。
- [ ] ジョブ成功、ローカルHTTP、利用者経路からの表示を分けて記録した。
- [ ] クリーンアップと元のVM・複製の正常性を確認した。
- [ ] 最終削除、または継続利用の費用・担当者を記録した。
- [ ] 元VM停止後、通常復旧先VNetへ実フェールオーバーしてコミットした。
- [ ] Region BでHTMLを更新し、更新後のマーカー・時刻をVM外へ記録した。
- [ ] BからAへの再保護を完了し、更新後の復旧ポイントを確認した。
- [ ] Bを停止してAへフェールバックし、更新後のマーカー一致を確認してコミットした。
- [ ] AからBへの再保護を完了し、保護状態を正常に戻した。
- [ ] 実リージョン障害と業務全体のRTO／RPOは未検証と説明できる。

次に考えること：

1. VM起動後にDNS・認証・外部DBが使えなかったら、業務は再開できるか。
2. より新しい復旧ポイントを選ぶことと、復旧の速さにはどのような関係があるか。
3. 実際にRegion Bで業務を再開した場合、Region Aへ戻す前に何が必要か。

## 9. 発展課題：システム全体の復旧

実フェールオーバーとフェールバックは本編です。追加で検証する場合は、DNS・利用者経路、認証・外部DB、複数VMの起動順序、バックグラウンド処理の排他、業務全体の再開条件を別途定義します。

**テスト用VMの削除はフェールバックではありません。** 本編では通常復旧先で更新したHTMLを逆方向に複製して戻し、さらに元方向の保護を再確立します。
