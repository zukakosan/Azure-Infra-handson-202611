# IaaS 補足：よくあるハマりどころとトラブルシューティング

[全体・進捗チェック](../../01-IaaS-ASRによるDRハンズオン.md) | [クリーンアップ](./08-クリーンアップ.md)

演習中に困ったときに参照してください。

## 1. まず確認すること

- **操作対象**：元VM、テスト用VM、現在稼働中の復旧VMを取り違えていないか。VM名・リージョン・VNetを確認します。
- **現在の工程**：テストフェールオーバー、実フェールオーバー、再保護のどの操作か。現在の稼働先と複製方向を確認します。
- **ジョブの状態**：Recovery Servicesコンテナーの **Site Recoveryジョブ** で、対象ジョブの状態とエラー詳細を確認します。ジョブ成功とWeb表示成功は別に確認します。

管理者へ確認するときは、ページ・Step、対象VM・リージョン、ジョブID・エラー、最後に成功した確認を伝えます。秘密情報を共有しないでください。

## 2. よくあるハマりどころ

| 状況 | 確認・対応 |
|---|---|
| Bashコマンドを手元で実行してエラーになる | 各ページの`bash`コードは、Bastionで対象のUbuntu VMへログインした後に実行します。手元のPowerShellやCloud Shellでは実行しません |
| パッケージの更新・インストールに失敗 | VMの送信通信、名前解決、配布先、パッケージ管理のエラーを確認します。成功を確認してから次へ進みます |
| 復旧ポイントがない／複製異常 | 初期複製、エージェント、送信通信、キャッシュストレージを確認します |
| フェールオーバーでVM作成に失敗 | ジョブの詳細、権限、復旧先のクォータ、VMサイズの容量、ネットワーク設定を確認します |
| 元の公開IPで復旧先へアクセスできない | 元VMの公開IPは復旧先へ引き継がれません。復旧先NICに関連付けた公開IPと、ブラウザーで開いたURLを確認します |
| VMは起動したがBastionで接続できない | 対象VMのVNet・プライベートIP、Bastion、NSG、ルートを確認します。公開IPはHTTP確認用で、SSHの接続先にはしません |
| Apacheが起動しない | 下の診断コマンドで設定・サービス状態・ログを確認します。復旧先で再インストールして成功扱いにしません |
| VM内のcurlは成功、ブラウザーは失敗 | 対象の公開IP、TCP 80のNSG・OS Firewall、ルート、参加者のHTTP接続経路を確認します。Bastionログイン成功とHTTP到達は別です |
| HTMLが既定ページ／内容不一致 | 更新後の復旧ポイント、保存先ディスク、対象VM、ブラウザーキャッシュを確認します。復旧先でHTMLを上書きして成功扱いにしません |
| テスト用VMを削除したのに元のリージョンへ戻っていない | テストのクリーンアップはフェールバックではありません。実切り替え後に戻す手順は[07：フェールバックと再保護](./07-フェールバックと再保護.md)です |
| 再保護が選択できない | フェールオーバーのコミット状態、戻す先のリージョン・権限・リソース、ジョブの状態を確認します |
| 再保護が完了しない／更新後の復旧ポイントがない | ジョブ詳細、キャッシュストレージ、送信通信、容量を確認します。解消するまでフェールバックへ進みません |
| VM操作がRead-onlyロックで拒否される | ASRの保護状態を確認し、ロックを手動解除して回避しません。フェールバック前のBの停止が拒否された場合は[07の10.1](./07-フェールバックと再保護.md#101-戻す準備を確認しportalからregion-bのvmを停止する)の代替手順に従い、停止完了も確認します |
| フェールバック後のマーカー不一致 | Bで控えたマーカー、更新後の復旧ポイント、戻したVMを確認します。Aで同じHTMLを作り直して成功扱いにしません |
| クリーンアップ後もリソースや課金が残る | テストVMの削除だけでは演習環境全体は削除されません。[08：クリーンアップ](./08-クリーンアップ.md)で複製無効化、専用リソースの削除、残存リソースを確認します |

### Apacheの診断コマンド

対象のUbuntu VMへBastionでログインして実行します。エラーが出ても後続の診断を確認できるよう、1行ずつ実行してください。

```bash
sudo apache2ctl configtest
sudo systemctl status apache2 --no-pager
sudo journalctl -u apache2 --no-pager -n 50
```

## 3. 作業を停止する条件

- ジョブが失敗した、または自分で設定した待機上限を超えた。原因を確認せず再試行したり、通常のフェールオーバーでテストを代替したりしません。
- テスト用VMから本番へ通信できた。演習を中止し、VMを停止・隔離して影響を確認します。
- 実フェールオーバー／フェールバック中に両リージョンのWebが稼働している。稼働先とデータを確認し、元VMを無条件に起動しません（隔離したテストVMとの同時稼働は除く）。
- 切り替え前に必要な復旧ポイントや停止状態を確認できない、または切り替え後にWeb表示やHTMLマーカーが一致しない。コミットせず、対象・ジョブ結果・表示内容を確認します。
- 削除対象に共有リソースや他の保護対象が含まれている。削除やロックの強制解除は行いません。

権限・ポリシー・クォータなど参加者が変更できない問題はサブスクリプション管理者へ確認します。

## 4. 結果を解釈するときの注意

- **ジョブ成功 ≠ 業務復旧**：VM内のHTTP応答、利用者経路からの表示、HTMLマーカーをそれぞれ確認します。
- **今回の所要時間 ≠ 業務全体のRTO**：実障害の検知・承認、本番DNS、認証、DB、外部依存、全利用者の復旧は検証していません。時間をメモする場合は起点・終点とタイムゾーンをそろえます。
- **マーカー一致 ≠ RPOゼロの保証**：HTML更新時刻と復旧ポイントを照合するため、マーカーと`Write completed at UTC`はVM外の任意のメモに控えます。表示内容の保持は確認できますが、実障害時のデータ損失ゼロやファイル全体の完全一致を保証するものではありません。
