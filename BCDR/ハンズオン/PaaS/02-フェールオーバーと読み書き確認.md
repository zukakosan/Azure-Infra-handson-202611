## このページの手順

### Step 3：計画フェールオーバーを実行する

1. PortalのFailover Groupで、サーバーAがPrimary、サーバーBがSecondaryであり、複製が正常であることを再確認します。
2. 切り替えにより既存のSQL接続が切断され得ることを確認し、承認者の許可を得ます。
3. **フェールオーバー（Failover）** を選択します。データ損失を許容する **強制フェールオーバー** は選択しません。
4. 確認画面の対象と切り替え方式を確認し、実行時刻を記録します。データ損失を許容する確認が表示された場合は進めず講師へ連絡します。
5. Portalの通知・Activity Logなどで操作結果を確認します。
6. サーバーBがPrimary、サーバーAがSecondaryに変わったことを記録します。

**確認結果**：計画フェールオーバーが成功し、両サーバーの役割が交換されること。

計画切り替えは、Primaryが利用可能な状態でデータを同期してから役割を変更します。Primaryが利用できない実障害の再現ではありません。待機上限を超えた場合はエラーと状態を記録し、強制切り替えで代替しません。

### Step 4：同じ接続先で再接続し、読み書きを確認する

1. SQLクライアントで既存の接続を閉じ、**同じリスナー名・同じ演習DB名**で新しい接続を確立します。
2. [Step 1](./01-接続確認とデータ登録.md)の接続確認SQLを実行し、現在のPrimaryであるサーバーBへの接続を確認します。
3. [Step 2](./01-接続確認とデータ登録.md)のSELECTで、切り替え前に登録したRecordIdと内容が残っていることを確認します。
4. 次のSQLで、切り替え後の新しいデータを登録・再取得します。

```sql
INSERT INTO dbo.DrExerciseRecords (RecordId, ExerciseKey, Phase)
OUTPUT inserted.RecordId, inserted.ExerciseKey, inserted.Phase, inserted.CreatedAtUtc
VALUES (NEWID(), N'<自分の演習キー>', N'after-failover');

SELECT RecordId, ExerciseKey, Phase, CreatedAtUtc
FROM dbo.DrExerciseRecords
WHERE ExerciseKey = N'<自分の演習キー>'
ORDER BY CreatedAtUtc, RecordId;
```

5. 接続確認SQLと一覧取得を、5秒以上の間隔で3回連続して成功させ、時刻を記録します。INSERTは毎回繰り返しません。

**確認結果**：リスナー名を変えずに新Primaryへ再接続でき、切り替え前のデータ参照と切り替え後の登録が成功すること。

接続に失敗した場合は、時刻・エラー・再試行回数を記録します。指定された間隔で上限時間内だけ再接続を確認し、超過時は講師へ連絡します。サーバーB個別の接続先への変更を、リスナーでの成功として記録しません。
