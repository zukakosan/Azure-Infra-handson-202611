# 5. Front Doorフェールオーバーの仕組み

## この章のゴールと位置付け

**オリジン選択と正常性判定を理解し、演習で何を観測すればよいか説明できること**がゴールです。アジェンダの60分のハンズオン枠に対応する事前解説で、リソース作成手順は含みません。

## 5.1 Front Doorの構成要素

| 要素 | 役割 | 演習で確認すること |
|---|---|---|
| プロファイル | Standard／Premiumの構成を管理する単位 | 対象プロファイルとSKU |
| エンドポイント | Front Door側のアクセス入口 | 利用者がアクセスするホスト名 |
| ルート | ドメインやパスをオリジングループに対応付ける | 対象パス、転送先、プロトコル、キャッシュ |
| オリジングループ | オリジン集合とプローブ・負荷分散設定 | Primary／Secondaryの両方が所属しているか |
| オリジン | 実際の転送先アプリ | ホスト名、Hostヘッダー、ポート、優先度、有効状態 |

オリジンのホスト名とHostヘッダー、TLSの証明書名が整合している必要があります。App Serviceへの直接アクセスが成功していても、Front Doorからの設定やアクセス制限によって失敗する場合があります。

## 5.2 オリジンが選ばれる順序

通常の選択では、次の順序で候補が絞られます。

1. 有効で、プローブにより正常と判断されたオリジンを選ぶ。
2. 候補の中から、最も高い優先度のオリジンを選ぶ。
3. レイテンシ感度の範囲内にあるオリジンを選ぶ。
4. 残った候補に重みに応じてトラフィックを配分する。

優先度の設定範囲は1～5で、小さい値が優先です。演習例はPrimaryを1、Secondaryを2にします。

**重みを変えるだけでは、優先度の異なる両系へ通常時の通信を分散できません。** 重みによる配分を試す場合は、同じ優先度とレイテンシの選択条件も確認します。また、少数リクエストの結果が設定比率と一致するとは限りません。

## 5.3 ヘルスプローブは何を正常と判断するか

Front Doorのプローブでは、HTTP `200 OK`を成功と判断します。その他のステータスや応答を取得できない場合は失敗です。

| 設定 | 意味 | 注意点 |
|---|---|---|
| プロトコル | HTTP／HTTPS | 転送先ポート、TLS、通信許可と整合させる |
| メソッド | HEAD／GET | 既定のHEADにアプリが対応しているか確認 |
| パス | 例：`/health` | 認証やリダイレクトで200以外にならないか |
| 間隔 | プローブ送信の頻度 | 短くするとオリジン負荷も増える |
| Sample size | 判定に使う直近の応答数 | 単発の成功・失敗ではなく複数サンプルで評価 |
| Successful samples required | 正常とみなすための成功数 | 感度と一時的な失敗への耐性が変わる |

例として、Sample sizeが4、Successful samples requiredが3なら、直近4回のうち3回以上が成功したときに正常と判断します。直近4回がすべて成功した状態から失敗が続くと、2回失敗した時点で成功数が2となり正常条件を満たさなくなります。

ただし、**「間隔×失敗回数」が必ず実際の切り替え時間になるわけではありません。** 障害が発生したタイミング、応答待ち、エッジごとの判定、利用者のアクセス間隔などが影響します。各エッジからプローブが送られるため、アプリには設定間隔だけから想像するより多くのプローブが届く場合があります。

### `/health`の設計

- 副作用のない軽量な処理にする。注文登録などの書き込みを行わない。
- HEADを使うならHEADでも正常に200を返す。
- 正常応答にシークレットや内部構成を含めない。
- 「プロセスが生存」と「業務処理を受けられる」を区別する。
- 必要な依存先を確認する場合、共有DBの障害で両系が同時に異常にならないか考える。

両リージョンが同じDBに依存し、そのDB障害で両方のプローブが失敗すると、リージョン切り替えでは解決できません。正常性判定に何を含めるかは業務と依存関係から決めます。

## 5.4 全オリジン異常時の重要な例外

オリジングループの全オリジンでプローブが失敗すると、Front Doorは全オリジンを異常と判断したうえで、ラウンドロビンでトラフィックを送ります。

「プローブが異常なら、そのオリジンへ絶対に通信しない」とは言えません。両系の正常性、利用者のエラー率、依存先の障害を合わせて観測します。無効化したオリジンは通常の転送候補から除外されるため、有効状態とプローブ異常を区別します。

## 5.5 キャッシュとセッションの影響

| 要素 | 観測を誤りやすい理由 | 演習の条件 |
|---|---|---|
| Front Doorのキャッシュ | オリジンへ到達せず古いリージョン表示を返し得る | 切り替え確認用ルートのキャッシュを無効にする |
| ブラウザーのキャッシュ | 再読み込みで古い画面が見える場合がある | アプリ側のキャッシュ制御と、実リクエストの発生を確認 |
| セッションアフィニティ | セッションの接続先が観測に影響する | 基本演習では無効にし、有効化は発展課題にする |
| アプリ内のローカル状態 | 接続先変更でログイン状態などを失う | 本番では状態の外部化や再接続時の動作を設計 |

キャッシュ回避を、URLに適当なクエリ文字列を付けることだけに依存しません。ルートのクエリ文字列キャッシュ動作によっては同じキャッシュが使われます。

## 5.6 演習の完了条件

設定が保存できただけでは完了としません。以下を揃えて完了とします。

1. **設計値**：正常時とPrimary異常時の期待オリジン、プローブ設定
2. **設定値**：ルート、グループ、各オリジンの優先度・有効状態
3. **確認結果**：直接アクセス、プローブ、Front Door経由の応答先と時刻
4. **説明**：期待どおりだった理由、未検証事項、目標との差分

観測では、障害開始から最初のSecondary成功までと、その後の安定した成功を分けます。アクセス頻度と確認場所を記録し、1回成功しただけで全利用者の復旧を断定しません。

## 理解確認

1. Primaryの優先度1、Secondaryの優先度2のまま重みを同じにすると半分ずつ流れるか。
2. `/health`が302を返す場合、プローブは正常か。
3. 両系のプローブが失敗した場合、Front Doorは何をするか。

**確認の観点**：通常は優先度1の正常なPrimaryが選ばれる／302は失敗／全系異常時のラウンドロビン動作がある。
