# 6. 障害注入、復旧、フェールバック

## この章のゴールと位置付け

**安全に障害を模擬し、利用者影響と復旧条件を記録し、戻す判断まで説明すること**がゴールです。アジェンダの20分の演習枠に対応する事前解説です。

## 6.1 障害を起こす前に決めること

- 演習専用の対象リソースと、影響を受ける通信
- 期待する状態変化と、確認に使うURL・プローブ・ログ
- 作業者、承認者、連絡先
- 中止条件と、障害注入を解除する方法
- 障害前の設定値、正常応答、両リージョンの状態
- Secondaryが使えることと、他の参加者や本番環境に影響しないこと

元の値を記録してから変更します。対象や復元方法が確認できない場合は障害を注入しません。

## 6.2 安全な障害注入と再現範囲

| 方法 | 模擬すること | 注意点と解除方法 |
|---|---|---|
| Primaryアプリを停止 | オリジンが応答できない状態 | 演習アプリだけを対象にし、再起動して正常性を確認 |
| `/health`だけを異常にする | 正常性判定により候補から外れる状態 | 利用者向け処理は動き続ける場合がある。通常応答に戻す |
| アプリの障害モードを有効化 | 設計したエラーや応答不能 | 影響するパスとプローブを明示し、元の設定へ戻す |
| Front Doorからのアクセスを一時拒否 | 特定経路の接続失敗 | 直接接続と転送の違いを確認。変更前の規則へ戻す |

どの方法も、リージョン全体の障害を完全に再現するものではありません。再現した条件と、未検証の依存先を明記します。

**リソース削除、データ破壊、本番トラフィックを使った障害注入は行いません。** 基本演習では、解除が容易なアプリ停止または事前準備済みの障害モードを優先します。

## 6.3 時刻と利用者影響の測定

| 記号 | 記録する時刻・状態 |
|---|---|
| t0 | 障害注入が有効になった時刻 |
| t1 | 観測上、Primaryのプローブが異常になった時刻 |
| t2 | Front Door経由で最初にSecondaryの成功応答を確認した時刻 |
| t3 | 事前に決めた回数・期間で成功が継続した時刻 |
| t4 | Primaryの障害注入を解除した時刻 |
| t5 | Primaryの正常性が回復したことを観測した時刻 |
| t6 | Front Door経由でPrimaryへの復帰を確認した時刻 |

- `t2 - t0`：観測条件下で最初のSecondary成功までの時間
- `t3 - t0`：演習で定義した安定したWeb応答までの時間
- 利用者影響：利用者側の失敗、タイムアウト、遅延が続いた区間

上記を同じものとして扱わないことが重要です。切り替え中も利用者の通信が成功する場合や、最初の成功後にエラーが混在する場合があります。

時刻はタイムゾーン、観測場所、アクセス間隔とともに記録します。ログ・メトリックの表示遅延がある場合、画面を見た時刻とイベントの時刻を区別します。t1やt5を取得できない場合は「未取得」とし、推定時刻を事実として埋めません。

業務全体のRTO評価では、データ、認証、依存先を含めた業務再開時刻を別途記録します。この演習ではデータ損失を測れないため、RPOの実測欄は「対象外」とします。

## 6.4 切り替わらないときの切り分け

| 観測結果 | 次に確認すること |
|---|---|
| Secondaryへの直接アクセスも失敗 | アプリの起動、依存先、容量、認証 |
| 直接アクセスは成功、プローブは失敗 | HEAD／GET、パス、200応答、TLS、アクセス制限 |
| 両系正常なのに期待先と異なる | 優先度、有効状態、対象ルート、セッション、キャッシュ |
| プローブ異常後もPrimaryの画面が出る | キャッシュ、全系異常の例外、実応答元、観測時刻 |
| SecondaryでWebは成功、業務は失敗 | DBの役割、接続先、RBAC、秘密情報、通信経路 |

設定をまとめて変更せず、期待値と観測値の差から原因を絞ります。変更した項目、理由、再試験結果を記録します。

## 6.5 フェールバックは独立した変更として扱う

データを持たない基本演習では、Primaryが正常に戻り優先度1のまま有効であれば、通常の選択条件でPrimaryが再び選ばれます。

本番ではSecondary稼働中に新しいデータが増えるため、「元のPrimaryを起動して戻す」だけでは不十分です。

1. 障害原因を解消し、Primaryの基盤・アプリ・容量を確認する。
2. 現在の正しいデータと書き込み先を確定する。
3. 必要な逆方向同期・レプリケーション再構成を行い、整合性を確認する。
4. アプリの接続先、認証、通信経路、バックグラウンド処理の所有者を確認する。
5. 書き込み停止や役割変更が必要な場合は、その順序と利用者影響を合意する。
6. 承認後にトラフィックを戻し、業務処理を再試験する。
7. Secondaryの待機状態、複製、バックアップ、監視を再確立する。

アプリとDBのPrimaryは常に同じリージョンである必要はありませんが、採用する構成のレイテンシ、可用性、書き込み先を明確にします。

両リージョンが独立に書き込みを受けてデータが分岐する状態を避けます。Front DoorだけでDBやバッチ処理の排他を保証することはできません。

承認前の自動復帰を避けたい場合は、Primaryの正常性だけでなく、オリジンの有効状態や業務受け入れ条件を制御する設計が必要です。手動の構成変更には反映時間と管理操作への依存があるため、それもテストします。

## 6.6 ランブックと定期テスト

ランブックには、発動条件、担当者、必要権限、操作、期待結果、停止・切り戻し条件、通知先を記載します。参照先が障害リージョンだけにある状態を避けます。

DRテストは、業務重要度や変更頻度に応じて定期実施し、アプリ、データ、ネットワーク、認証の重要な変更後にも再検証します。例えば四半期の部分試験と年次の全体訓練を組み合わせる場合も、頻度は組織の要件から合意します。

テスト結果はRTO／RPO、データ整合性、残存容量、判断時間、通知、フェールバックまで評価し、未達事項に担当者と改善期限を付けます。

## 理解確認

1. t2でSecondaryが1回応答しただけで、全利用者の復旧を宣言してよいか。
2. Secondaryで新規注文を受け付けた後、古いDBを使うPrimaryへ戻してよいか。
3. RTOを超えた原因が承認待ちの場合、アプリの改善だけで解決するか。

**確認の観点**：観測範囲と安定性の確認が必要／正しいデータと書き込み先の確認が必要／判断・承認の運用も改善対象。
