# 7. DRチェックリスト、まとめ、Q&A

## この章のゴール

**設計と演習の結果から、確認済み事項と本番化に向けた未確認事項を整理すること**がゴールです。アジェンダの最後の10分に対応します。

以下のシートは座学と演習で使う記入用です。未確認の項目を想定値で「確認済み」にせず、未確認として残します。

## 7.1 DRチェックリスト

### 業務要件と障害シナリオ

- [ ] 復旧する業務フローと、その正常判定を定義した。
- [ ] 業務担当者とRTO／RPO、代替業務、許容データ損失を合意した。
- [ ] インスタンス、ゾーン、リージョン、誤更新などを区別した。
- [ ] DRの発動条件、判断者、承認者、連絡先を決めた。

### 基盤とアプリケーション

- [ ] 復旧先リージョンのサービス対応、データ所在地、容量を確認した。
- [ ] 復旧先で同じリリース、設定、イメージを利用できる。
- [ ] クォータと残存リージョンの処理能力を検証した。
- [ ] セッション、ローカルファイル、バックグラウンド処理の扱いを決めた。
- [ ] 障害時の管理APIやデプロイ基盤への依存を洗い出した。

### データと通信・認証

- [ ] 複製方式、複製遅延、利用可能な復旧ポイントを確認した。
- [ ] 誤更新や誤削除に対するバックアップと復元試験を用意した。
- [ ] 書き込み先、役割変更、再接続、再試行を検証した。
- [ ] DNS、証明書、Private Link、Firewall、オンプレミス経路を確認した。
- [ ] 復旧先のID、RBAC、シークレット、暗号化キーの利用を確認した。

### 運用と検証

- [ ] 両系のプローブと利用者視点の監視を用意した。
- [ ] DRランブックと記録先を障害時にも参照できる。
- [ ] 安全な障害注入、中止、復元の条件を定義した。
- [ ] 切り替えだけでなく業務再開とデータ整合性を確認した。
- [ ] フェールバックの同期、承認、再試験、待機系再確立を検証した。
- [ ] 定期テスト、変更後テスト、改善担当者と期限を決めた。

## 7.4 簡易DRランブックのひな形

| 工程 | 判断・作業内容 | 担当・承認者 | 証拠・完了条件 |
|---|---|---|---|
| 障害判定 | 利用者影響、両系の正常性、依存先を確認 |  | 障害範囲とDR発動条件を満たす根拠 |
| DR発動 | データ損失、復旧方式、影響を確認して承認 |  | 承認記録と復旧目標 |
| 復旧準備 | データ、容量、認証、経路を確認 |  | 復旧先が業務を受け入れられる |
| 切り替え | データの役割と入口を定義した順序で変更 |  | 正しい書き込み先と通信先 |
| 動作確認 | 代表業務、データ整合性、性能を確認 |  | 合意した成功条件と観測記録 |
| 関係者通知 | 影響、再開範囲、未復旧事項を連絡 |  | 通知記録と次回報告時刻 |
| フェールバック | 原因解消、同期、承認後に戻す |  | Primaryで業務正常、Secondary再待機 |
| 振り返り | 目標との差分と未検証事項を整理 |  | 改善担当者、期限、再試験予定 |

各操作には対象、必要権限、具体的な手順、期待結果、中止・切り戻し条件を追記します。資格情報の秘密値は記載せず、承認された取得・利用方法への参照を使います。

## 7.5 よくある質問

### 2リージョンに置けばDRは完成か

いいえ。データ、認証、ネットワーク、外部依存、容量、判断と復旧手順まで含めて検証します。

### Front DoorでDBも自動的に切り替わるか

いいえ。Front DoorはHTTP／HTTPSの転送先を選びます。DBの役割変更や接続先、書き込みの整合性は別途設計します。

### ヘルスプローブ間隔を短くすればRTOを保証できるか

いいえ。検知以外に承認、データ復旧、容量、アプリの準備、業務確認が必要です。エッジごとの判定や観測条件も影響します。

### レプリケーションがあればバックアップは不要か

いいえ。誤更新や削除が複製先へ伝わる場合があります。過去の正常な時点への復元を別途備えます。

### Primaryが復旧したら、すぐ戻してよいか

いいえ。Secondaryで増えたデータ、正しい書き込み先、同期、業務受け入れ条件と承認を確認してから戻します。

## 7.6 発展課題

- 同一優先度と重みによる配分を試し、短時間の観測と設定比率を比較する。
- セッション状態を持つアプリで、切り替え時の利用者影響を整理する。
- プローブのパス・間隔・サンプル条件を変え、検知と負荷の関係を比較する。
- Azure Monitorのアラートを用意し、通知時刻と実際の事象時刻を比較する。
- 手動切り替えを、権限・承認・期待結果まで含むランブックへ具体化する。
- [第2章の3つの業務](../02-RTO-RPOとDRパターン/02-RTO-RPOとDRパターン.md)に対し、方式と未検証の前提を説明する。

データストアや追加サービスを用いる課題は基本演習の外です。事前に範囲、費用、権限、後片付けを確認します。

## まとめ

1. BCDRは、業務の重要度と障害シナリオから始める。
2. RTOとRPOを分け、方式名ではなく復旧条件で判断する。
3. 通信切り替えと、データを含む業務再開を混同しない。
4. フェールバックまでテストし、未達事項を継続的に改善する。
