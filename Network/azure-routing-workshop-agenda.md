# Azure ルーティング設計・トラブルシューティング ワークショップ

## 1. 概要

- **想定時間**: 3時間10分（座学60分、休憩10分、ハンズオン120分）
- **対象者**: Azureの基本操作とVNetの基礎を理解しているインフラ／クラウド担当者
- **形式**: 講義、デモ、ハンズオン、障害解析チャレンジ
- **主なサービス**: Azure Virtual Network、VNet Peering、Route Table、UDR、Azure Firewall、Network Watcher、（クラス共用デモ）VPN Gateway（BGP）

## 2. 到達目標

ワークショップ終了後、受講者が以下を実施できることを目標とする。

- Azureにおけるパケット転送とルート選択の仕組みを説明できる
- システムルート、VNetピアリング、UDRの役割を理解できる
- Hub-Spoke構成で、UDRにより通信をAzure Firewallへ集約し、NVAを使う場合との設定上の違いを説明できる
- BGPの広告・学習とSpokeへの経路伝達を区別し、GatewayとNICの両方で経路を確認できる
- Network Watcherを使って、疎通障害の原因を切り分けられる
- 非対称ルーティングやNSGによる通信遮断の典型例を説明できる

### 4.1 Azureルーティングの基礎

- Azure上でルートが決まるまでの流れ
- システムルート
- ユーザー定義ルート（UDR）
- BGPから伝播されたルート
- ルート選択の優先順位
  - 最長プレフィックス一致
  - UDR、BGP、システムルートの関係
- ネクストホップの種類
  - `VirtualAppliance`
  - `VirtualNetworkGateway`
  - `VnetLocal`
  - `Internet`
- NIC、サブネット、VNet間でのパケットの流れ
- NSGとルートテーブルの役割の違い

### 4.2 代表的な構成と設計ポイント

- VNetピアリング
- Hub-Spokeネットワーク
- Azure Firewall／NVA経由の集中ルーティング
- Gateway TransitとRemote Gateway
- オンプレミス接続時のVPN／ExpressRoute
- VNetピアリングが推移的ではないことによる設計上の注意
- 非対称ルーティングが発生する典型例
- Azure Virtual WAN／Azure Route Serverの位置付け

### 4.3 トラブルシューティング

- NICの有効なルート
- Network Watcher
  - Connection troubleshoot
  - Next hop
  - IP flow verify
  - Network topology
  - Packet capture
- VNetフローログ（既存環境のNSGフローログは移行対象として扱う）
- DNS障害とルーティング障害の見分け方

### 4.4 よくある失敗

- UDRの関連付け先とプレフィックスの誤り
- ピアリングの非推移性と転送トラフィック許可の取り違え
- NVAのAzure NIC側とOS／製品側のIP転送設定の不一致
- 復路の不足と非対称ルーティング
- NSGのステートフル動作と新規接続・応答の混同
- ゲートウェイ共有、経路伝達、明示的な送信方式の不足
- DNS・アプリケーション障害、ログの未取得との混同

## 5. ハンズオン：Hub-Spoke、UDR、BGPによる経路確認

事前課題（構築担当者）：[Bicepによる班別環境のデプロイ](./ハンズオン/00-事前環境のデプロイ.md)。授業前に展開と開始状態の確認を完了し、以下のハンズオン120分には含めない。

本文・事前準備は[ハンズオンの進め方](./ハンズオン/00-NWハンズオンの進め方.md)を参照する。FW演習は班別のAzure Firewall環境、BGP演習はFWを置かないクラス共用の独立環境を使用する。VPN Gatewayはクラス全体で2台だけを講師が事前構築し、受講者は広告・学習・経路の観測を行う。初稿ではAzure Firewallを基準とし、NVAへの置き換えは別教材とする。

1. [Hub-SpokeとUDR](./ハンズオン/01-Hub-SpokeとUDR.md)：班別環境でピアリング、FW折り返し、直接経路を比較
2. [BGPによる経路広報と確認](./ハンズオン/02-BGPによる経路広報と確認.md)：FWとは独立したクラス共用環境で広告・学習・経路伝達を確認
3. [障害解析とAI活用](./ハンズオン/03-障害解析とAI活用.md)：障害カード、調査手順、記録シート

### 5.1 演習の目的

班別のHub-Spoke構成において、Spoke間通信をAzure Firewallへ転送する往復経路を構成する。UDRなし・直接ピアリング・具体的なUDRの違いを比較し、有効なルート、Next hop、ping（ICMP）、FWログで確認する。HTTPサーバー起動は基本演習に含めず、TCP試験は待ち受けサービスを事前準備した場合だけの任意課題とする。BGPはFW演習と分離したクラス共用のVPN Gateway環境で、広告・学習とSpokeへの経路伝達を確認する。受講者がVPN Gatewayをデプロイしたり、班別FW環境と共有したりしない。

### 5.2 演習環境

```text
班別：FW演習（班ごとに独立。VPN Gatewayなし）
Spoke 1 ── VNet Peering ── Hub + Azure Firewall ── VNet Peering ── Spoke 2

クラス共用：BGP演習（FW演習とは独立。講師がVPN Gateway 2台を事前構築）
共有Spoke ── VNet Peering / Gateway Transit ── BGP Hub + VPN Gateway
                                                   ║ VNet-to-VNet VPN / BGP
模擬オンプレミス ─────────────────────────── VPN Gateway 2
```

図のHub-Spoke / Firewallは班ごとの環境で、VPN Gatewayを配置しない。BGPは別のクラス共用環境で実施し、班別Firewall環境とは接続しない。BGPの共有資源は読み取り専用とし、切替操作は講師が行う。

### 5.3 演習手順

1. 班別環境でHub・Spokeの範囲、VMの試験サービス、FWの状態を確認する
2. Hub-Spokeの相互ピアリング後、状態が両方向とも`Connected`であることを確認する
3. 直接SpokeピアリングもUDRもない状態で、Spoke間の経路が存在せずpingが失敗することを確認する
4. 往復UDRを関連付け、両VMの相手宛てNext hopがFWの`VirtualAppliance`であることを確認する
5. 両方向のping疎通とFWのICMP `Allow`ログを確認する
6. 一時的な直接Spokeピアリングで、直接経路・`/0`UDR・具体的`/16`UDRのNext hopがどう変わるかを確認する
7. 直接ピアリングと一時UDRを削除し、両方向のFW経由通信が復旧したことを確認する
8. 講師が提示するクラス共用BGP環境で、GatewayのBGPピア状態、広告・学習経路を確認する
9. 共有SpokeへのGateway Transitと経路伝達の設定・有効なルート・疎通結果を確認する。経路伝達の切替は講師が操作し、受講者は変更前後を観測する

### 5.4 期待結果

- Spoke間通信が往復とも意図したAzure Firewallを経由する
- 送信元VMのNICで、対象プレフィックスのネクストホップが`VirtualAppliance`として表示される
- Network WatcherのNext hopで、想定した次ホップが確認できる
- Firewall側で対象ICMP通信のログが確認できる
- 直接ピアリングがある場合、`/0`UDRだけではFWを経由しない理由を説明できる
- BGPの広告・学習と、Gateway Transit／経路伝達によるSpokeへの適用を区別して説明できる。経路伝達の切替時の期待値は講師の実機予行で確認したものを用いる

## 6. 障害解析チャレンジ

講師側で、以下のいずれかを1つだけ意図的に設定する。具体的な注入・切り戻しと提出用シートは[障害解析とAI活用](./ハンズオン/03-障害解析とAI活用.md)を参照する。

- UDRのアドレスプレフィックスが間違っている
- 片側のサブネットにルートテーブルが関連付いていない
- FWの規則が対象ICMP通信を拒否している
- NSGがICMP Echo Requestをブロックしている（任意のTCP試験では新規接続と許可済み接続の応答を区別する）
- 戻り経路がない（別経路を通る非対称ルーティングとは区別する）
- Spoke 1だけゲートウェイルート伝達が無効になっている（クラス共用BGP環境で講師デモのみ）

受講者は以下の情報を使って原因を特定する。

- NICの有効なルート
- Next hop
- NSG diagnostics（ICMPの評価）
- 任意のTCP試験ではIP flow verify、Connection troubleshoot
- NSG／Firewall／NVAログ

時間と承認済みAI環境がある場合は、取得した事実からAIに仮説・確認順序を整理させる。AIの回答は実際の診断結果で検証し、自動変更は行わない。AIがなくても演習は完了できる。

## 8. 運営上の注意

- Azure Firewallはプロビジョニングに時間とコストがかかるため、原則として事前展開する
- VPN Gatewayはクラス共用の独立したBGP環境に2台だけ事前展開する。FWは共有せず班別環境に分け、受講者はBGPの広告・学習・共有Spokeへの伝達を確認する。共用Gateway／ピアリング／ルート設定の変更は講師に限定する
- 120分のハンズオン枠ではFW／VPN／VMの新規展開を行わず、ピアリング・UDR・伝達設定と観測に集中する
- 各手順に「正常時の期待結果」を記載する
- 受講者ごとに環境を用意するか、2～3人で1環境を共有する
- 演習終了後に、作成したリソースを削除する手順を案内する
