# 2. 代表的な構成と設計ポイント

## この章のゴールと対象範囲

[前章](./01-Azureルーティングの基礎.md)のルート選択を踏まえ、通信要件に応じてVNetピアリング、Hub-Spoke、ゲートウェイ共有を使い分けます。特に「接続すること」と「通信を検査すること」を分けて設計します。

この章の構成例は考え方を学ぶためのものです。本番環境に必要なSKU、冗長構成、サブネットサイズ、コストの確定や、リソースの作成手順は対象外です。

## 2.1 全章共通の構成例

| 役割 | アドレス |
|---|---|
| Hub VNet | `10.0.0.0/16` |
| HubのFirewall / NVA用サブネット | `10.0.1.0/24` |
| Firewall / NVAのプライベートIP | `10.0.1.4` |
| Spoke 1 VNet / VM用サブネット / VM 1 | `10.1.0.0/16` / `10.1.1.0/24` / `10.1.1.4` |
| Spoke 2 VNet / VM用サブネット / VM 2 | `10.2.0.0/16` / `10.2.1.0/24` / `10.2.1.4` |

Azure Firewallを採用する場合は、専用サブネット名`AzureFirewallSubnet`など、サービス固有の要件にも従います。`10.0.1.4`は説明用の値であり、実際には割り当てられたプライベートIPを使用します。

```text
Spoke 1                         Hub                          Spoke 2
10.1.0.0/16                     10.0.0.0/16                  10.2.0.0/16
VM 1 -- VNet Peering -- Firewall / NVA -- VNet Peering -- VM 2
10.1.1.4                        10.0.1.4                     10.2.1.4
```

この図ではSpoke同士の直接ピアリングはありません。Hubとのピアリングだけでは、図に描いたSpoke間の転送はまだ成立しません。

## 2.2 VNetピアリング：2つのVNetを直接接続する

VNetピアリングは、VNet間をMicrosoftのバックボーン経由で接続する仕組みです。相互に通信を許可する構成では、相手VNetのアドレス空間への経路が追加されます。

重要なのは、**通常のVNetピアリング自体には推移性がない**ことです。Spoke 1とHub、HubとSpoke 2が接続されていても、Spoke 1からSpoke 2へHubが自動的にパケットを中継するわけではありません。

Spoke間通信には、要件に応じて次のいずれかを選びます。

| 要件 | 主な選択肢 | 注意点 |
|---|---|---|
| Spoke同士を直接接続したい | Spoke間の直接ピアリング | Firewall検査を自動的に経由するわけではない |
| Spoke間通信を検査したい | HubのFirewall / NVAとUDR | 往復経路、転送許可、検査ポリシーが必要 |
| 多拠点・多VNetの接続を集約したい | Virtual WANなど | 通常のピアリングとはルーティングモデルが異なる |

直接ピアリングの基本構成ではVNetのアドレス空間を重複させません。Azure内だけでなく、オンプレミスや将来接続するネットワークを含めてアドレス計画を立てます。

> Microsoft Learn：[Azure 仮想ネットワーク ピアリング](https://learn.microsoft.com/ja-jp/azure/virtual-network/virtual-network-peering-overview)  
> ピアリングの接続性、サービスチェイニング、ゲートウェイ共有を確認できます。

## 2.3 Hub-Spoke：共有機能とワークロードを分離する

Hubには、オンプレミス接続、Firewall、DNSなどの共有機能を集約し、Spokeには個々のワークロードを配置します。

この分離により、共通の通信方針を管理しやすくなります。一方で、Hubを作っただけで通信が集約されるわけではありません。どの通信をHubへ送り、どの通信を直接接続にするかを明示する必要があります。

設計を始めるときは、製品の一覧より先に通信要件を表にします。

| 通信 | 検査の要否 | 想定経路 |
|---|---|---|
| Spoke 1からSpoke 2 | 必要 | Spoke 1 -> HubのFirewall -> Spoke 2 |
| Spokeからインターネット | 必要 | Spoke -> HubのFirewall -> 外部 |
| Spokeからオンプレミス | 組織の要件による | ゲートウェイへ直接、またはFirewall経由 |
| 同一Spoke内のVM間 | 組織の要件による | VNet内で直接、または別途設計した検査経路 |

この表をもとに往路・復路のUDR、セキュリティ規則、ログの取得点を決めます。ネットワークを分けることと、必要な通信を拒否することも同義ではありません。実際の隔離はNSGやFirewallなどで実現します。

> Microsoft Learn：[Azureのハブスポーク ネットワーク トポロジ](https://learn.microsoft.com/ja-jp/azure/architecture/networking/architecture/hub-spoke)  
> HubとSpokeの責務、接続方法、運用上の設計判断を深めるための参照アーキテクチャです。

## 2.4 Spoke間の通信をFirewall / NVAに集約する

### 往路と復路のUDR

VM 1とVM 2の通信をHubで検査する場合、説明用の最小構成では次のUDRを使用します。

| 適用先のサブネット | 宛先プレフィックス | 次ホップの種類 | 次ホップIP |
|---|---|---|---|
| Spoke 1のVM用サブネット | `10.2.0.0/16` | `VirtualAppliance` | `10.0.1.4` |
| Spoke 2のVM用サブネット | `10.1.0.0/16` | `VirtualAppliance` | `10.0.1.4` |

往路は`VM 1 -> Firewall / NVA -> VM 2`、復路は`VM 2 -> Firewall / NVA -> VM 1`です。Hub側には、各Spokeへ到達できるピアリングなどの経路が必要です。

この例は元のプライベートIPを維持する通信を想定しています。SNATを行う構成では、宛先から見える送信元IPと復路設計が変わるため、同じ経路図をそのまま使わずに確認します。

### 経路以外にも必要な設定

| 確認対象 | Azure Firewall | VMベースのNVA |
|---|---|---|
| 転送先 | FirewallのプライベートIP | NVAの転送用プライベートIP |
| 転送処理 | マネージドサービスの動作と経路を確認 | Azure NICのIP転送と、ゲストOS / 製品側の転送を確認 |
| 通信許可 | Firewall Policyなどの適切な規則 | 製品側のポリシー、必要なNSGやOS設定 |
| 可用性 | 可用性ゾーンなどのサービス構成を検討 | 製品が対応する冗長化・経路切替を設計 |

ピアリングでは、Hubのアプライアンスが転送したパケットをSpokeで受信できる設定も必要です。設定は「どちらが相手からの転送トラフィックを受け入れるか」という方向で確認します。相互通信では、各SpokeがHubからの転送トラフィックを受け入れられるようにします。

**転送トラフィックを許可する設定は、転送経路を作る設定ではありません。** UDR、ピアリングの許可、アプライアンスの転送、通信許可のすべてが揃って初めて成立します。

VMベースのNVAは、原則としてワークロードとは別サブネットに置きます。ワークロード向けのUDRをNVA自身にも適用すると、ループを作るおそれがあります。

> Microsoft Learn：[ルーティングの概要：カスタムルート](https://learn.microsoft.com/ja-jp/azure/virtual-network/virtual-networks-udr-overview#custom-routes)  
> 仮想アプライアンスの次ホップ、IP転送、配置上の注意を確認してください。

## 2.5 インターネット向け通信：既定ルートと送信方式をセットで設計する

Spokeのインターネット向け通信をHubへ集約する代表的な方法は、`0.0.0.0/0 -> VirtualAppliance -> FirewallのIP`というUDRです。

ただし、これは「より具体的な経路に一致しない通信」を誘導する設定です。VNet内やピアリング先の具体的なルートまで、すべてFirewallへ向かうわけではありません。

出口では、FirewallのSNATなど、実際に外部へ通信するための仕組みと許可規則も必要です。検査が不要で送信元IPの固定などが目的なら、NAT Gatewayも選択肢ですが、NAT Gateway自体はFirewallのような通信検査を行いません。

2026年3月31日以降にリリースされたAPIでは、新規VNetのサブネットは既定でプライベートとなり、暗黙の既定送信アクセスに依存できません。既存環境の動作まで一律に変わるわけではないため、実際のサブネット設定と利用APIも確認します。教材や本番設計では、暗黙の外部接続を前提にせず、明示的な送信方式を用意します。

> Microsoft Learn：[Azureでの既定の送信アクセス](https://learn.microsoft.com/ja-jp/azure/virtual-network/ip-services/default-outbound-access)  
> プライベートサブネットと明示的な送信接続方式の関係を確認できます。

## 2.6 オンプレミス接続：VPN / ExpressRouteとゲートウェイ共有

VPNはIPsecによる接続、ExpressRouteは接続事業者などを通じたプライベート接続を提供します。いずれも、回線やトンネルが正常であることと、目的の宛先経路が揃っていることは別です。

HubのゲートウェイをSpokeで共有する際の基本的な関係は次のとおりです。

| 側 | 設定の意味 |
|---|---|
| Hub側 | 自分のゲートウェイをピアリング先で使用できるようにする（Gateway Transit） |
| Spoke側 | Hubのリモートゲートウェイを使用する（Use Remote Gateways） |

Spokeが自分のゲートウェイを持つ場合など、共有には構成上の制約があります。ゲートウェイ共有は、通常のピアリングを無条件に推移的にする設定でも、Firewall検査を有効にする設定でもありません。

オンプレミスからSpokeへの復路、必要な経路の広告、Spoke側でのゲートウェイルート伝達も確認します。`GatewaySubnet`のルート伝達を無効にするとゲートウェイの動作に影響するため、無効化しません。

また、オンプレミス向け通信を検査する場合は、Hub・ゲートウェイ側を含めた往復経路を個別に設計します。Spoke側のUDRを追加するだけでは、検査経路の対称性は保証できません。

> Microsoft Learn：[仮想ネットワーク ピアリングのVPNゲートウェイ転送を構成する](https://learn.microsoft.com/ja-jp/azure/vpn-gateway/vpn-gateway-peering-gateway-transit)  
> Hub側とSpoke側の設定の役割を、具体的な構成で確認できます。

## 2.7 Virtual WANとRoute Serverの位置付け

| 選択肢 | 解決したい課題 | 混同しないこと |
|---|---|---|
| 自前のHub-Spoke | 共有サービス、検査経路、接続を自分で設計・管理したい | ピアリングだけではSpoke間転送は成立しない |
| Azure Virtual WAN | 多拠点・多リージョンの接続をマネージドハブで集約したい | ハブルートテーブルや関連付け・伝播など、独自の設計が必要 |
| Azure Route Server | NVAとAzureの間でBGPを使った動的な経路交換を行いたい | Route Server自体がデータパケットを中継・検査するわけではない |

Route Serverは経路を交換する制御プレーンです。NVAの代わりになるFirewallではありません。Virtual WANも、導入するだけですべての通信が自動的に意図した検査経路を通るとは限りません。

このワークショップでは、基本動作を追いやすい自前のHub-SpokeとUDRを中心に扱います。

> Microsoft Learn：[Virtual WANを使用するハブスポーク ネットワーク トポロジ](https://learn.microsoft.com/ja-jp/azure/architecture/networking/architecture/hub-spoke-virtual-wan-architecture)
>
> Microsoft Learn：[Azure Route Serverとは](https://learn.microsoft.com/ja-jp/azure/route-server/overview)

## 2.8 理解度チェック

1. Hubと2つのSpokeをピアリングするだけで、Spoke間通信は成立しますか。
2. Spoke 1だけにSpoke 2向けUDRを追加すれば、Firewall経由の双方向通信を保証できますか。
3. Route Serverを配置すれば、NVAの通信検査機能を置き換えられますか。

### 解答と解説

1. 通常のピアリングだけでは成立しません。直接ピアリング、またはアプライアンスなどによる転送経路が必要です。
2. 保証できません。Spoke 2の復路、ピアリングの転送許可、Firewallの規則なども必要です。
3. 置き換えられません。Route Serverは経路交換を行い、実際の検査・転送は対応するアプライアンスなどが担当します。
