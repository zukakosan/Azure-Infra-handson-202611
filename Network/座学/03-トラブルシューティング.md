# 3. トラブルシューティング

## この章のゴールと対象範囲

「つながらない」という現象を、名前解決、経路、通信許可、転送処理、アプリケーションに分けて調べます。設定を思いつきで変更するのではなく、観測結果から次に確認する場所を決めることが目標です。

[前章](./02-代表的な構成と設計ポイント.md)のVM 1（`10.1.1.4`）からVM 2（`10.2.1.4`）へ、HubのFirewall / NVA（`10.0.1.4`）を通してTCP接続するケースを共通例にします。ここではVM間通信を中心に扱い、PaaS固有の診断は対象外とします。

## 3.1 最初に通信条件を固定する

同じ「接続できない」でも、送信元、宛先、ポートが違えば原因も変わります。調査前に次の情報を揃えます。

| 項目 | 記録例 |
|---|---|
| 発生時刻 | 日時とタイムゾーン。ログ検索でも同じ時刻基準を使う |
| 送信元 | VM 1、NIC、`10.1.1.4`、所属サブネット |
| 宛先 | VM 2、`10.2.1.4`、必要ならFQDN |
| 通信条件 | TCP、宛先443、実際の送信元ポート |
| 期待する経路 | VM 1 -> `10.0.1.4` -> VM 2 |
| 現象と範囲 | タイムアウト、接続拒否、特定VMのみ、変更後から発生など |

送信元ポートが未確認なら「未確認」と記録します。診断で仮の送信元ポートを使った場合、その結果はその条件での評価であり、実通信と一致するかを確認します。

繰り返し試験するときは、NSGなどの既存セッションの影響を避けるため、新しい接続で再現性を確認します。ネットワーク全体を許可する、NSGを外す、複数のUDRを同時に変える、といった変更は原因の特定を難しくするため避けます。

## 3.2 調査は「名前解決 → 経路 → 許可 → 転送 → 待ち受け」で進める

| 段階 | 確認すること | 次に進む判断 |
|---|---|---|
| 1. 名前解決 | FQDNが想定するIPへ解決されるか | 違うIPならDNSを調べる。IPが確定したらそのIPの経路へ |
| 2. 経路 | 送信元NICの有効なルートとNext hop | 次ホップが違えば、UDR・関連付け・伝播を調べる |
| 3. 通信許可 | NSG、Firewall、OSなどの許可 | 拒否が見つかれば、該当する規則と要件を照合する |
| 4. 転送と復路 | アプライアンスが転送し、応答も戻るか | 片方向だけなら、復路や状態追跡を調べる |
| 5. アプリケーション | ポートで待ち受け、期待する応答を返すか | TCP到達後のTLS・認証・アプリケーションへ進む |

実際には、接続のトラブルシューティングを最初に実行して調査先を絞っても構いません。大切なのは、ある段階の正常結果を他の段階の正常証明にしないことです。

FQDNの接続先と同じIPへのTCP接続を比較すると、DNSとネットワークの問題を分離しやすくなります。ただし、HTTPSで単純にURLをIPへ置き換えると、証明書やSNI、Hostヘッダーの違いで失敗する場合があります。IPへのTCP到達性と、FQDNでのアプリケーション応答は別に評価します。

## 3.3 有効なルート：設定の意図ではなく、NICへの適用結果を見る

ルートテーブルリソースに正しいUDRがあっても、別サブネットに関連付いていれば対象VMには適用されません。VMのネットワーク画面などからNICの「有効なルート」を確認し、次の観点で読み取ります。

- 宛先IPを含むプレフィックスが存在するか。
- そのルートの由来が、システム、ユーザー、ゲートウェイなどのどれか。
- 状態が有効か。無効な候補がある場合、どのルートに置き換わっているか。
- 次ホップの種類とIPが期待どおりか。
- より具体的な別経路がないか。

共通例では、VM 1からVM 2への宛先`10.2.1.4`について、`10.2.0.0/16 -> VirtualAppliance -> 10.0.1.4`が期待値です。復路はVM 2のNICで`10.1.0.0/16`を確認します。

有効なルートはAzure側の適用経路を確認する情報です。ゲストOS内の経路、NVAの転送処理、宛先アプリケーションの状態は別途確認します。表示・取得には、対象VMの稼働状態や権限などの条件もあります。

> Microsoft Learn：[仮想マシンのルーティングに関する問題を診断する](https://learn.microsoft.com/ja-jp/azure/virtual-network/diagnose-network-routing-problem)  
> 有効なルートの確認手順と、UDR・IP転送に関する診断の観点を確認できます。

## 3.4 Network Watcherの機能を使い分ける

| 機能 | 答えたい問い | 結果だけでは分からないこと |
|---|---|---|
| Next hop | このVMからこの宛先IPへ、Azureはどの次ホップを選ぶか | その先の転送成功、復路、TCP接続の成功 |
| IP flow verify | 指定した方向・IP・ポート・プロトコルをNSGが許可するか | Firewall、OS、アプリケーションの許可・状態 |
| Connection troubleshoot | 指定した接続がその時点で成立するか、どこに問題の兆候があるか | 継続的な正常性や、すべての装置の内部状態 |
| Topology | どのネットワークリソースがどう接続されているか | 実パケットが通った経路や到達性 |
| Packet capture | VMで実際にどのパケットが送受信されているか | 取得していない別の地点での動作 |

Network Watcherが対象リージョンで利用できること、必要な権限があることを事前に確認します。拡張機能、対応OS、到達性などの前提は機能によって異なります。たとえばPacket captureではエージェントの要件を確認します。Connection troubleshootにはエージェントレスのプレビューもあるため、「すべての機能で拡張機能が必須」とは考えません。

### Next hop：特定の宛先に絞る

有効なルートが多い場合、Next hopに送信元VMと宛先`10.2.1.4`を指定すると、その宛先に対する次ホップを確認できます。

期待値が`VirtualAppliance / 10.0.1.4`なのに別の種類やIPが返る場合は、送信元サブネットへの関連付け、プレフィックス、より具体的な経路を見直します。期待値どおりなら、経路をむやみに変更せず次の段階を調べます。

### IP flow verify：方向と5つの条件を揃える

IP flow verifyでは、方向に加えて送信元IP、宛先IP、送信元ポート、宛先ポート、プロトコルを意識します。VM 1からの送信を確認する場合と、VM 2への受信を確認する場合では、対象VMと方向が変わります。

`Allow`はNSG評価上の許可であり、エンドツーエンドの接続成功ではありません。`Deny`なら、表示された規則を確認し、サブネットとNICに適用されたNSGの関係も調べます。

### Connection troubleshoot：接続全体の兆候をつかむ

共通例では、送信元をVM 1、宛先を`10.2.1.4`、TCPの宛先ポートを443にして調べます。接続状態、到達できない兆候、NSGや経路に関する診断結果を、他の観測結果と組み合わせます。

タイムアウトと接続拒否も区別します。接続拒否は待ち受けがない場合や装置が明示的に拒否する場合などに発生しますが、エラー表示だけで原因を断定せず、宛先のプロセスとログを確認します。

> Microsoft Learn：[Azure Network Watcherとは](https://learn.microsoft.com/ja-jp/azure/network-watcher/network-watcher-overview)
>
> Microsoft Learn：[ネクストホップの概要](https://learn.microsoft.com/ja-jp/azure/network-watcher/network-watcher-next-hop-overview)
>
> Microsoft Learn：[IPフロー検証の概要](https://learn.microsoft.com/ja-jp/azure/network-watcher/ip-flow-verify-overview)
>
> Microsoft Learn：[接続のトラブルシューティングの概要](https://learn.microsoft.com/ja-jp/azure/network-watcher/connection-troubleshoot-overview)

## 3.5 Firewall / NVAと復路で止まっていないかを確認する

次ホップが正しいのに通信できない場合、次の順で観測します。

1. Firewall / NVAに、対象通信のログやパケットが到着しているか。
2. 到着した通信が許可・転送されているか。
3. 宛先VMまで要求パケットが届いているか。
4. 宛先VMは応答を返しているか。
5. 応答が同じ検査経路を戻っているか。

Firewallログが見つからないだけでは、「届いていない」とは断定できません。診断設定、ログの種類、検索条件、時刻、転送遅延も確認します。

VMベースのNVAでは、Azure NICのIP転送とOS / 製品側の転送を分けて調べます。マネージドのAzure Firewallに、利用者管理のLinux NVAと同じOS操作を行うことはありません。

パケットキャプチャでTCPのSYNが宛先に届き、SYN-ACKが宛先から送られているのに送信元で観測できない場合は、復路や途中のフィルタリングを重点的に調べます。NATがある構成では、変換前後でIP・ポートが異なる点に注意します。

> Microsoft Learn：[パケットキャプチャの概要](https://learn.microsoft.com/ja-jp/azure/network-watcher/packet-capture-overview)  
> VMでの送受信を実際のパケットで確認する際の機能と前提を確認できます。

## 3.6 フローログと装置ログを組み合わせる

フローログは、送信元・宛先IP、ポート、方向、通信量などの情報を使い、どのような通信が発生したかを追うためのものです。パケットの本文やアプリケーションの処理結果まで記録するパケットキャプチャではありません。

| 情報源 | 主な使い方 |
|---|---|
| VNetフローログ | VNetを流れる通信の傾向や対象フローの有無を確認する |
| Firewall / NVAログ | 適用された許可・拒否規則、通信や変換の情報を確認する |
| OS / アプリケーションログ | サービス起動、接続受付、TLS・認証エラーなどを確認する |

新しい環境ではVNetフローログを前提にします。NSGフローログは2025年6月30日以降の新規作成ができず、2027年9月30日に廃止予定です。既存環境でNSGフローログを使用している場合は、VNetフローログへの移行を検討します。

ログは有効化していなかった過去にさかのぼって取得できません。また、ログの未記録は通信がなかった証明とは限りません。対象リソースの対応範囲、記録条件、保存先、反映時間を確認します。保存容量、保持期間、Traffic Analyticsなどのコストも設計します。

> Microsoft Learn：[仮想ネットワーク フローログの概要](https://learn.microsoft.com/ja-jp/azure/network-watcher/vnet-flow-logs-overview)
>
> Microsoft Learn：[NSGフローログの概要と廃止に関する案内](https://learn.microsoft.com/ja-jp/azure/network-watcher/nsg-flow-logs-overview)

## 3.7 切り分けの例：Next hopは正常なのにTCP接続できない

VM 1からVM 2のTCP 443への接続がタイムアウトしたとします。

| 観測結果 | 解釈と次の確認 |
|---|---|
| VM 1のNext hopは`10.0.1.4` | VM 1側の次ホップは設計と一致。UDRを変更する前に先を確認する |
| 対象の送信・受信条件でNSGは許可 | NSG以外の制御や転送を確認する |
| NVAで要求を受信するが、VM 2向けの送信が見えない | NVAの転送設定、製品ポリシー、経路を確認する |
| NVAのOS側のIP転送が無効 | Azure NIC側の設定だけでは転送できなかったと判断する |

是正後は、NVAからの送信だけで完了とせず、宛先の受信、応答、送信元の受信、アプリケーション応答まで確認します。

調査結果は「現象」「観測した事実」「原因」「変更内容」「再試験結果」に分けて残します。推測を事実と混ぜないことで、別の担当者も同じ判断を再現できます。

## 3.8 理解度チェック

1. IP flow verifyが`Allow`なら、Firewallも許可していますか。
2. Topologyに接続が描かれていれば、その経路で実通信が成功したと言えますか。
3. Next hopが想定どおりなのに接続できないとき、最初にUDRを追加すべきですか。

### 解答と解説

1. 言えません。NSGの評価とFirewallの評価は別です。
2. 言えません。構成上の接続と、実際のパケットの到達性は別です。
3. いいえ。次ホップ以降の転送、フィルタリング、復路、宛先の待ち受けを確認します。
