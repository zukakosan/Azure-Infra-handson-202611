# 4. よくある失敗

## この章のゴールと使い方

この章では、[ルーティングの基礎](./01-Azureルーティングの基礎.md)、[構成設計](./02-代表的な構成と設計ポイント.md)、[トラブルシューティング](./03-トラブルシューティング.md)を、実際に起こりやすい失敗へ結び付けます。

各例を「症状 → 原因 → 確認する証拠 → 是正・予防」の順で読みます。症状だけでは原因を一意に決められないため、同じ症状が出たら必ず示された証拠を確認してください。

## 4.1 UDRは正しいのに、対象VMに適用されていない

**症状**：ルートテーブルには`10.2.0.0/16 -> 10.0.1.4`があるのに、VM 1のNext hopが想定と違います。

**典型的な原因**：ルートテーブルを作成しただけで関連付けていない、別のサブネットに関連付けた、送信元ではなく宛先側だけに設定した、といった適用先の取り違えです。

**確認する証拠**：

- VM 1の実際のNICと所属サブネット。
- そのサブネットに関連付いたルートテーブル。
- VM 1の有効なルートと、`10.2.1.4`宛てのNext hop。

**是正・予防**：送信元サブネットへの関連付けを修正します。作業手順には「作成できたこと」ではなく「対象VMの有効なルートに反映されたこと」を完了条件として記載します。

## 4.2 `0.0.0.0/0`を設定すれば、すべてFirewallを通ると思っている

**症状**：外部向け通信はFirewallを通る一方、直接ピアリングしている別Spokeへの通信はFirewallログに出ません。

**典型的な原因**：`0.0.0.0/0`のUDRより、ピアリング先の`10.2.0.0/16`などの具体的なルートが優先されています。これはルート選択の基本動作です。

**確認する証拠**：宛先IPに一致する候補のプレフィックス長と、実際のNext hopを比較します。Firewallログの有無だけで経路を判断しません。

**是正・予防**：検査対象のSpoke宛てについて、適切な具体的プレフィックスのUDRを設計します。Spoke間の直接接続を許すかも含めて構成を見直します。サービスエンドポイントのルートなど、上書きできない例外は別に確認します。

> Microsoft Learn：[Azureによるルート選択の仕組み](https://learn.microsoft.com/ja-jp/azure/virtual-network/virtual-networks-udr-overview#how-azure-selects-routes-for-traffic-routing)

## 4.3 Hubとピアリングすれば、別Spokeにも自動的に届くと思っている

**症状**：Spoke 1からHub、Spoke 2からHubには接続できるのに、Spoke間では通信できません。

**典型的な原因**：通常のVNetピアリングを推移的な接続と考えています。Hub VNet自体が、別のピアリングへ自動中継するルーターになるわけではありません。

**確認する証拠**：Spoke間の直接ピアリングの有無、Hubの転送装置の有無、各SpokeのUDRとNext hopを確認します。

**是正・予防**：直接接続が目的なら直接ピアリングを、検査が目的ならFirewall / NVAを経由する往復経路を用意します。接続図に線を引くだけでなく、各通信の次ホップを記載します。

> Microsoft Learn：[Azure 仮想ネットワーク ピアリング](https://learn.microsoft.com/ja-jp/azure/virtual-network/virtual-network-peering-overview)

## 4.4 NVAのAzure NICだけでIP転送を有効にしている

**症状**：Next hopはNVAで、NVAでも要求を受信していますが、宛先へ転送されません。

**典型的な原因**：Azure NICのIP転送は有効でも、ゲストOSの転送が無効、またはNVA製品のポリシーが拒否しています。逆に、OS側だけ有効でAzure NIC側が無効な場合もあります。

**確認する証拠**：Azure NIC設定、OS / 製品側設定、NVAでの受信・送信パケット、製品の拒否ログを分けて確認します。

**是正・予防**：製品の推奨構成に従い、Azure側とOS / 製品側の両方を整えます。マネージドのAzure Firewallに、Linux NVA向けのOS設定手順を流用しないようにします。

## 4.5 ピアリングの転送許可を、経路やFirewall規則と混同している

**症状**：UDRとアプライアンスの設定は想定どおりでも、Hubで中継された通信をSpokeが受信できません。

**典型的な原因**：Hubからの転送トラフィックを受け入れるSpoke側のピアリング設定が不足しています。あるいは、転送許可さえ有効なら経路や装置の許可も作られると思っています。

**確認する証拠**：各方向のピアリング設定、UDR、NVAの転送、NSGとFirewallの評価結果を確認します。相互通信では両Spokeを確認します。

**是正・予防**：「Hubから転送されたパケットを、このSpokeが受け入れるか」という向きで設定を確認します。転送許可、経路、通信許可を別々のチェック項目にします。

## 4.6 往路だけFirewallを通し、復路を設計していない

**症状**：要求はFirewallに届きますがTCP接続が成立しない、または接続が不安定です。

**典型的な原因**：片側のUDRだけ設定し、応答が別経路を通っています。状態を追跡するFirewall / NVAが接続の片方向しか観測できず、期待する状態が成立しない場合があります。

**確認する証拠**：

- VM 1とVM 2の両方で、相手IP宛てのNext hopを確認する。
- 要求と応答がそれぞれどこまで観測できるかを確認する。
- SNATを使用している場合は、変換後の送信元と復路を確認する。

**是正・予防**：必要な往復経路を揃え、製品の冗長化方式も含めて状態追跡と整合させます。単にNSGの逆向き規則を追加しても、非対称な経路は直りません。

> Microsoft Learn：[Azureのハブスポーク ネットワーク トポロジ](https://learn.microsoft.com/ja-jp/azure/architecture/networking/architecture/hub-spoke)

## 4.7 NSGがステートフルであることを忘れている

**症状**：拒否規則を追加したのに既存のSSH接続が継続するため、「規則が効いていない」と判断します。または、許可済み接続の応答のために不要な広域許可を追加します。

**典型的な原因**：新規接続と既存接続、要求とその応答を区別していません。

**確認する証拠**：新しい接続で再試験し、対象のIP・ポート・プロトコル・方向とNSGの評価結果を確認します。既存セッションが続くことだけでは、設定失敗とは判断しません。

**是正・予防**：許可された接続の応答用に、広い逆向き許可を追加しないようにします。相手から新たに開始する接続は別に評価します。サブネットとNICの両方にNSGがある場合、片方の許可だけでは不十分であることも確認します。

> Microsoft Learn：[ネットワーク セキュリティ グループの概要](https://learn.microsoft.com/ja-jp/azure/virtual-network/network-security-groups-overview)

## 4.8 オンプレミスの経路を受け取る設定を外している

**症状**：Hubからオンプレミスへ接続できるのに、Spokeからは接続できません。

**典型的な原因**：Gateway TransitとUse Remote Gatewaysの組み合わせ、Spoke側のゲートウェイルート伝達、オンプレミス側への経路広告などが不足しています。

**確認する証拠**：Spokeの有効なルートにオンプレミスのプレフィックスがあるか、オンプレミス側にSpokeへの復路があるかを確認します。トンネルや回線が正常という情報だけで、経路が揃っているとは判断しません。

**是正・予防**：共有設定と経路伝達を意図した状態へ修正します。ゲートウェイルート伝達を無効化する場合は必要な代替経路を設計し、`GatewaySubnet`では無効化しません。

ExpressRoute Gatewayを、VPN Gatewayと同じようにUDRの`VirtualNetworkGateway`で任意に指定しようとしないことも重要です。

> Microsoft Learn：[VPNゲートウェイ転送の構成](https://learn.microsoft.com/ja-jp/azure/vpn-gateway/vpn-gateway-peering-gateway-transit)
>
> Microsoft Learn：[カスタムルートとゲートウェイの制約](https://learn.microsoft.com/ja-jp/azure/virtual-network/virtual-networks-udr-overview#custom-routes)

## 4.9 ルートと許可があるので、インターネットへ出られると思っている

**症状**：VM間通信はできるのに、OS更新や外部APIへの接続に失敗します。

**典型的な原因**：プライベートサブネットで明示的な送信方式を用意していない、FirewallのSNATや規則が不足しているなど、実際の出口が成立していません。

**確認する証拠**：宛先IPへのNext hop、サブネットの送信アクセス設定、NAT Gatewayなどの関連付け、Firewallの送信処理、名前解決を確認します。

**是正・予防**：検査要件に応じてAzure FirewallやNAT Gatewayなどの適切な出口を用意します。「Internetルートがある」「NSGが許可している」「外部へ送信できる」を別の確認項目にします。

`0.0.0.0/0`を変更すると、インターネットからのSSH / RDP接続の応答経路も変わり、管理接続が切れる場合があります。変更前に影響と代替の管理経路を確認します。

> Microsoft Learn：[Azureでの既定の送信アクセス](https://learn.microsoft.com/ja-jp/azure/virtual-network/ip-services/default-outbound-access)

## 4.10 DNSやアプリケーションの問題を、ルーティングの問題として扱っている

**症状**：IPへのTCP接続は成功するのにFQDNで失敗する、またはTCP接続後にTLSエラーやHTTPエラーになります。

**典型的な原因**：名前解決先の誤り、DNS参照先の違い、証明書・SNI・認証・アプリケーション設定などが原因です。

**確認する証拠**：実際の接続元でのDNS応答、解決されたIP、TCP接続の結果、TLS・アプリケーションのログを比較します。

**是正・予防**：障害が起きている層を分離してから、DNSやアプリケーションの設定を修正します。FQDNを単純にIPへ置き換えたHTTPS試験は、同じ条件の試験にならないことに注意します。

## 4.11 ログがないことを、通信がない証拠にしている

**症状**：Firewallやフローログの検索で見つからず、「パケットが出ていない」と判断します。

**典型的な原因**：事前の有効化がない、対象リソースやログの種類が違う、時刻・IP・ポートの検索条件が違う、NATや取り込み遅延を考慮していません。

**確認する証拠**：診断設定、保存先、対象範囲、時刻基準、変換前後のアドレス、別地点でのキャプチャを確認します。

**是正・予防**：必要なログを事前に有効化し、正常時にも取得できることを確認します。新規環境はVNetフローログを前提とし、NSGフローログの新規作成を含む古い教材は更新します。

> Microsoft Learn：[仮想ネットワーク フローログの概要](https://learn.microsoft.com/ja-jp/azure/network-watcher/vnet-flow-logs-overview)

## 4.12 設計・変更前の最終チェック

- [ ] 通信要件を、送信元・宛先・プロトコル・ポートで具体化した。
- [ ] 接続するVNetとオンプレミスのアドレス空間が重複していない。
- [ ] 直接接続する通信と、検査する通信を区別した。
- [ ] 往路・復路のそれぞれで、適用するルートと次ホップを説明できる。
- [ ] UDRを正しい送信元サブネットへ関連付けた。
- [ ] ピアリングの転送許可、NVAの転送、NSG・Firewallの許可を別々に確認した。
- [ ] ゲートウェイ共有と経路伝達に必要な設定を確認した。
- [ ] 外部接続が必要な場合、明示的な送信方式を設計した。
- [ ] 管理接続への影響と、問題があった場合の切り戻し方法を確認した。
- [ ] 正常時の有効なルート、Next hop、疎通結果、ログを保存した。

## 4.13 理解度チェック

次の状況で、最初に何を確認するか説明してください。

1. Firewall向けの`0.0.0.0/0`があるのに、直接ピアリング先への通信がFirewallを通りません。
2. NVAのNICでIP転送を有効にしたのに、NVAに届いたパケットが先へ進みません。
3. VM 1からの要求はVM 2へ届き、VM 2も応答を送っていますが、VM 1では応答を受信できません。

### 解答と解説

1. より具体的なピアリングルートと、対象宛先へのNext hopを確認します。
2. OS / 製品側の転送設定、ポリシー、送信側での観測を確認します。
3. VM 2からVM 1へのNext hop、Firewall / NVAでの復路、NATの有無を確認します。観測した証拠から絞り込み、直ちにNSGの広域許可を追加しないようにします。

## ハンズオンへのつなぎ

ハンズオンでは、正常な構成で往復のNext hopと疎通を記録したうえで、UDRの関連付けやNVAの転送などを1項目ずつ変化させます。変更前後の証拠を比較し、どの観測結果から原因に到達したかを説明できることを目標とします。
